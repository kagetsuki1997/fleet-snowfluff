The original standalone `claude_cli.rs` (status detection) was later merged into `claude_code_cli.rs` itself — it had no other caller and its only genuinely reusable piece (`map_spawn_error`, generic across any CLI-backed provider) moved to a new small `cli_process.rs` instead, so Group 3's Codex work can share it without importing from a Claude-named module.

## 3. OpenAI/Codex subscription auth (experimental)

- [x] 3.1 (reworked from the original wording once live research corrected two assumptions — see design.md Context "Correction to an earlier pass") Added `providers/codex.rs` with a `Codex: AiProvider` implementation that spawns `codex exec --json --sandbox read-only -c model_instructions_file=<temp file with the persona> [resume <id>] "<latest user message>"`. Since Codex's assistant text arrives as one complete `item.completed`/`agent_message` event, not deltas, the reply is chunked client-side after the fact (reusing `Mock::chunk_text`) so the stream still paces out over time per the "Streaming responses" requirement's new scenario for this case. Verified by parsing literal fixture lines built from Codex's own published event-shape documentation (`thread.started`, `item.completed`/`agent_message`, `turn.failed`, top-level `error`, and several ignored event types) — not a live capture, unlike the Anthropic fixtures, since no subscription was available.
- [x] 3.2 Added `codex login status` detection (exit-code-based, unlike `claude auth status --json`'s structured output) mapping to the same `ProviderError` variants as the Anthropic path, sharing `cli_process::map_spawn_error` for the missing-binary case. Verified with tests over literal fixture outputs, same style as the Anthropic work.
- [x] 3.3 Investigated: no flag exists to disable tool access outright, but `--sandbox read-only` (the default) prevents shell command _execution_ entirely (confirmed via documentation) — narrower than Claude's `--disallowedTools` but covers the highest-severity risk (arbitrary command execution). Whether the reply _text_ still narrates/proposes tool use even though it can't execute is unconfirmed and documented as an open, experimental-gated question. Also investigated (not originally scoped, but the same class of question): no `--system-prompt` equivalent exists at all — `-c model_instructions_file=<path>` (OpenClaw's own mechanism) is used instead, with its precedence-vs-`AGENTS.md` behavior similarly unconfirmed.
- [x] 3.4 Added `ProviderProfile::is_experimental()` in `settings.rs` (a profile-level fact, not an `AiProvider` trait method) returning true only for `(OpenAi, Subscription)`. Verified with a test asserting exactly that combination reports experimental and every other combination does not.

## 8. Post-verification fixes (`/opsx:verify` findings)

An independent `/opsx:verify` pass against this change's own specs/tasks/design found three discrepancies after Group 7 was already checked off -- all three fixed in this group rather than left open, per the user's "fix all" instruction. See design.md's own Decisions entries (both newly added "Correction found during `/opsx:verify`" notes) for the full reasoning behind each.

- [x] 8.1 (CRITICAL finding) The "Subscription auth via the provider's own CLI" requirement's "CLI installed but not logged in" scenario asserted "the application attempts to trigger that CLI's own login flow" -- confirmed via grep that no code anywhere did this; only the read-only status checks and the fallback instruction text existed. Fixed by adding `AiProvider::trigger_login()` (default no-op `Ok(())`; overridden by `ClaudeCodeCli`/`Codex` to spawn `claude auth login`/`codex login` detached, reaped in a background task, never awaited to completion) and a new `trigger_profile_login` Tauri command (`ai_commands.rs`). Added a "Log in" button to each profile row's `<summary>` (`ui/src/main.ts`), shown only while status is `not_logged_in`, wired to call the new command and then re-check status. New locale key `ai.login_button` added identically to all 5 locale files.
- [x] 8.2 (WARNING finding) `Codex::list_models()`'s unconditional empty list contradicted the "Live model listing" requirement's text/scenario, which only described the Claude-shaped outcome (a confirmed alias set, "rather than an empty list"). Researched Codex CLI's actual documentation (developers.openai.com/codex -- the CLI isn't installed on this machine to check `--help` directly): unlike Claude Code's small, stable, named `--model` aliases, Codex's `model` config key takes an open-ended, frequently-revised version string with no enumerated list in its own docs (only example given: `model = "gpt-5.6"`); third-party sources for a fixed alias list disagreed with each other, exactly the "arbitrary guess" the requirement already warns against. Rather than hardcode unconfirmed, likely-to-go-stale values, amended the "Live model listing" requirement (`specs/ai-provider/spec.md`) to name both outcomes as valid: a confirmed alias set when a CLI's own docs give one, an empty list when they don't -- split into two scenarios accordingly. `codex.rs`'s doc comment and a new test (`list_models_is_empty_by_design_since_no_confirmed_alias_set_exists`) updated to match.
- [x] 8.3 (SUGGESTION finding) The AI tab's per-profile status was only ever fetched once, when the whole settings window opened, not when the user actually switched to the AI tab specifically -- a profile's CLI could log out or hit its quota while the user was on a different tab. Fixed in `ui/src/main.ts`'s tab-button click handler: switching to the `ai` tab now re-runs `refreshProfileStatus` for every profile slot (not a full `renderAi()`, which would discard any in-progress unsaved edits in the row's own inputs).
- [x] 8.4 Verified: `cargo build --workspace` clean; `cargo test --workspace` -- 175 passed (up from 174: +1 `Codex::list_models` empty-by-design test, the `trigger_login` methods themselves are untested subprocess side effects with no pure logic, matching the existing precedent that `chat()`/`check_logged_in()` also have no direct unit test beyond fixture-based parsing), 0 failed, 4 ignored; `tsc --noEmit` clean; `npm run build` clean; `i18n::tests::every_locale_parses_and_shares_the_same_key_set` still passes with the new `ai.login_button` key in all 5 locales.
