## Context

See `proposal.md` - Why for motivation. Constraints established by reading the existing codebase during discovery:

- `AiProvider` (`crates/fleet-snowfluff-ai/src/provider.rs`) is already transport-agnostic: `chat()` returns a boxed `Stream` of `StreamChunk`s regardless of how those chunks are produced. This change does not need to touch the trait itself.
- `ProviderKind` (`crates/fleet-snowfluff-ai/src/message.rs`) is a flat 4-variant enum; `AiSettings.active_provider: Option<ProviderKind>` (`crates/fleet-snowfluff-ai/src/settings.rs`) is a single pointer, with per-kind settings structs (`OpenAiSettings`, `AnthropicSettings`, `OllamaSettings`, `MockSettings`) stored independently but only one ever "active." `ProviderCredentials` (`crates/fleet-snowfluff-ai/src/credentials.rs`) holds exactly two fields, both API keys.
- `build_provider()` (`crates/fleet-snowfluff/src/ai_commands.rs:172`) is the single chokepoint that turns `(settings, credentials, ProviderKind)` into a `Box<dyn AiProvider>`. `chat_commands.rs:197` reads `settings.active_provider` to decide which one to build for a given chat request. Both currently assume "one active provider" as a given.
- `disclosure_ok()` (`ai_commands.rs:57`) currently keys acknowledgment per `ProviderKind` only (`settings.openai.disclosure_acknowledged`), with no concept of auth method.
- Verified live this session: `claude` CLI (v2.1.275) ships `auth login` / `auth logout` / `auth status` / `setup-token` subcommands. `claude auth status`, run non-interactively via a piped-stdio child process (no TTY), returned clean JSON (`loggedIn`, `authMethod: "claude.ai"`, `apiProvider: "firstParty"`, `subscriptionType: "pro"`) — confirming both that no separate `ant` CLI is needed and that headless status checks work cleanly.
- `codex exec --json` is the sanctioned non-interactive mode and delivers JSONL line-by-line (`thread.started`, `turn.*`, `item.*`). **Correction to an earlier pass of this document**: an earlier read of this conflated "delivered line-by-line" with "text streams incrementally" — they're different things. Confirmed via documentation (not live-tested — no OpenAI/Codex subscription available): the assistant's reply text itself arrives as exactly one complete `item.completed`/`agent_message` event, not delta-by-delta. Also confirmed via documentation: `codex exec` has no `--system-prompt`-equivalent flag at all (OpenClaw's own approach, and this change's, is `-c model_instructions_file=<path>`, a real documented Codex config key overridable from the command line); `--sandbox read-only` (the default) prevents shell command execution entirely, not just file writes; and `codex exec resume <SESSION_ID>` / `codex exec resume --last` provide the same session-continuity mechanism as `claude -p --resume`, resolving what an earlier pass of this document left as an open question ("does Codex support this at all") in the affirmative.
- This codebase already treats config migration as a first-class, tested concern: `AiSettings::sanitize` degrades field-by-field rather than discarding the whole file on a bad value, and `app-config`'s spec has a dedicated one-shot migration requirement (legacy Ameath config). This change's config migration follows that precedent rather than inventing a new one.
- **Superseded finding, corrected mid-implementation**: the first pass of this change had Anthropic's subscription path send an `Authorization: Bearer <token>` obtained from `claude setup-token` directly against the raw `/v1/messages` API. Two things falsified this before it shipped: (1) live testing showed `claude setup-token` is not a "peek at the current session's token" call at all — it's a full interactive OAuth ceremony that mints a new, long-lived (1-year) credential every time it runs, wrong for a per-request call; and (2) research confirmed that OAuth tokens from Claude Free/Pro/Max (`setup-token` included) are contractually restricted to Claude Code and claude.ai only — Anthropic's Consumer Terms of Service explicitly disallow using them against the Messages API from a third-party application, and the API rejects them outright regardless. Anthropic's subscription auth is therefore implemented as a subprocess wrapping `claude -p`, not raw HTTP — see "Anthropic subscription auth is `claude -p`, not raw HTTP" below.
- **OpenClaw's actual implementation, researched on request** (`docs.openclaw.ai/providers/anthropic` and its published CLI-bridge projects), since this project's source doc named OpenClaw as the direct reference for this whole feature: OpenClaw invokes `claude -p` for programmatic turns, detects auth via `claude auth status`, never reads/persists/forwards the native login token ("Claude owns the login and token refresh lifecycle" — validates this change's existing "nothing persisted" principle), and — the part that changes this change's design — **keeps a warm Claude Code session per conversation and resumes it with `--resume <session-id>` on later turns**, rather than spawning a stateless one-shot process per message. A fresh session pays full context/cache-creation cost; a resumed one is a cheap cache-read. Verified live this session (two trivial, reversible calls through an already-logged-in session, no new credentials minted): a fresh `claude -p --output-format stream-json --include-partial-messages` call cost ~13K cache-creation tokens for a one-sentence reply when run with default project settings inherited (this repo's own dev hooks leaking into context); adding `--strict-mcp-config --setting-sources ""` cut that to ~2.8K, and the _second_ call in the same session was a cache-read, not a fresh creation. The streamed events are `{"type":"stream_event","event": {...}}`-wrapped, and the inner `event` is structurally identical to Anthropic's own native SSE shape (`message_start`, `content_block_start`, `content_block_delta` with `text_delta`, `content_block_stop`, `message_delta`, `message_stop`) — the exact same shape `providers/anthropic.rs`'s existing `parse_sse_line` already matches on, just unwrapped from a `stream_event` envelope instead of an SSE `data:` line. `--system-prompt` fully replaces Claude Code's own system prompt (verified: a persona-flavored one-sentence system prompt produced an in-character, tool-free reply), and `--system-prompt-snapshot`'s default behavior (record once on the first turn, reuse verbatim on every resume) means the same `--system-prompt` flag can be passed on every call, first or resumed, without needing to special-case which turn is "the first."

## Goals / Non-Goals

**Goals:**

- Let a configured profile use either an API key or the provider's own subscription/CLI login, behind the same `AiProvider` interface, for Anthropic and OpenAI.
- Follow OpenClaw's own approach for both CLI-backed subscription providers: `claude -p` / `codex exec`, auth detection via the CLI's own status command, and (for Anthropic, where `--resume` is verified to work) a warm, resumed session per Fleet chat session rather than a fresh CLI process per message.
- Let more than one provider profile be enabled and configured at once (the data model and settings UI only), with a single manually-chosen default handling all chat requests.
- Preserve every existing Stage 1 guarantee (master switch, no-provider-by-default, disclosure-before-use, live model listing, streaming, bounded output/context, separate credential storage) under the new shape.
- Migrate existing Stage 1 configs losslessly into the new shape with no user action required.

**Non-Goals:**

- Task Routing or Fallback logic between enabled profiles (choosing per-message or on failure) — deferred to a later change. In this change, the default profile always handles every request; other enabled profiles exist only to be switched to manually.
- A verified, production-quality OpenAI/Codex subscription integration. It ships because the data model and UI need to support more than one subscription-capable provider, and because withholding it entirely would leave the "equal priority" auth-method work half-built — but it is explicitly experimental (see Risks) pending a tester with an actual ChatGPT/Codex subscription.
- Reimplementing OAuth for either provider. Both subscription paths are thin wrappers around each provider's own official CLI.
- Any change to `Message`, `Role`, or persona/prompt assembly — this change is about how a provider is authenticated and selected, not about what's sent to it.

## Decisions

**Anthropic subscription auth is `claude -p`, not raw HTTP — both providers converge on subprocess-wrapping, but not because symmetry was the goal.** The original plan (raw HTTP with a bearer token from `claude setup-token`) is invalid: rejected by the Messages API and a Consumer ToS violation regardless (see Context). The corrected implementation is a new provider, `providers::claude_code_cli::ClaudeCodeCli`, that spawns `claude -p --system-prompt <persona> --disallowedTools <fixed deny-list> --strict-mcp-config --setting-sources "" --output-format stream-json --include-partial-messages [--resume <session-id>] "<latest user message>"` and parses the resulting event stream by unwrapping `{"type":"stream_event","event": ...}` and matching the inner `event` with the same `content_block_delta`/`text_delta` logic `providers/anthropic.rs`'s `parse_sse_line` already has (extracted into a shared, reusable function rather than duplicated). `providers/anthropic.rs` itself is unchanged from Stage 1 — it only ever spoke API-key auth, and continues to. OpenAI's subscription auth remains a separate provider implementation spawning `codex exec --json`. _Alternative considered, now moot_: the original "raw HTTP is cleaner, keep it asymmetric" reasoning doesn't survive contact with Anthropic's actual auth-scoping rules — there is no working raw-HTTP path to choose over the subprocess one for a personal subscription. The trait-level point from that original reasoning still holds, though: nothing above `AiProvider` needs to know or care that this implementation's bytes come from a subprocess rather than a socket.

**A warm, resumed CLI session per Fleet chat session (OpenClaw's model), tracked in the app crate, not inside `fleet-snowfluff-ai`.** `ClaudeCodeCli`/`Codex` each hold an `Arc<Mutex<Option<String>>>` for their own session/thread id, populated from the id field present on every line of their event streams; `chat()`'s signature itself is unchanged (still `Vec<Message> -> Result<ChatStream, ProviderError>`). Reading the captured id back out, however, needed _some_ uniform way for the app crate's `Box<dyn AiProvider>` call sites to reach it without knowing the concrete type — resolved during app-crate integration (group 4) by adding `AiProvider::session_id(&self) -> Option<String>` as a small, additive trait method with a default `None` body (and, for the same reason, `AiProvider::check_availability()` for the settings UI's status check), rather than the inherent-method-only design floated when this decision was first written. Both are zero-cost for every existing provider (`Mock`, `Ollama`, `OpenAiCompatible`, API-key `Anthropic` — none of them change at all) and don't touch `chat()`'s own signature, so the substance of the original rejection below still holds; only the "not through the trait at all" detail was refined once an actual call site needed it. The app crate (`ChatRuntimeState` in `chat_commands.rs`) is where the resulting session id is actually kept across messages, keyed by `ProfileKey` — this is project-specific runtime state, so it belongs in the app crate, not in `fleet-snowfluff-ai` (preserving that crate's existing "depends on nothing project-specific" boundary from Stage 1). On a resumed turn, only the latest user message is sent as the CLI prompt (extracted from the tail of the `messages` argument) — the reconstructed context window `prompt::assemble_messages` built for every other provider is not replayed into an already-resumed session, since the CLI already remembers its own prior turns; a _fresh_ session (first use of this profile in a Fleet chat session, or after a resume fails) only gets the current message plus the persona system prompt, not earlier turns from a _different_ provider used earlier in the same Fleet chat session. _Alternative considered_: extend `AiProvider::chat()`'s own signature to carry a session hint in and out — rejected because it would force every provider (including the three that have no concept of a resumable session) to thread an unused parameter through, for a need that's specific to two implementations; a separate, default-provided accessor method achieves the same "trait stays a no-op for everyone else" goal without that.

**Session id is runtime-only, never written to disk.** Consistent with "nothing new is persisted for subscription auth" below: an app restart starts a fresh Claude-CLI session (losing the cache-read discount, not losing anything Fleet itself considers durable — the Fleet-level JSONL chat log remains the actual source of truth per Stage 1's existing design). _Alternative considered_: persist the session id in `ai-config.json` so a resume survives a restart — rejected as unnecessary complexity for a purely cost-driven optimization, and because a session id that outlives the process that minted it invites more staleness edge cases (has the CLI's own local session log been pruned? compacted?) than it saves.

**Config profiles replace the single active-provider pointer.** `AiSettings.active_provider: Option<ProviderKind>` becomes `enabled_profiles: Vec<ProviderProfile>` (each: provider brand, auth method, model, and — since disclosure is now per auth method, see below — its own `disclosure_acknowledged`) plus `default_profile: Option<ProfileId>`, manually set. `build_provider()` and the chat-request path resolve the default profile instead of a bare `ProviderKind`. _Alternative considered_: keep `active_provider` as-is and only add an `auth_method` field alongside it (Question 4's "(a) minimal" option) — rejected because it doesn't match the settings-UI shape this change commits to (an "available profiles" list, not a single radio choice), and because Stage 3's routing/fallback logic needs something to route between that would otherwise require a second migration later.

**Nothing new is persisted for subscription auth.** `ProviderCredentials`/`secrets.json` gains no new field, and Fleet never reads, stores, or mints a token of any kind for either CLI. A profile's `auth_method: Subscription` is enough non-secret state (lives in `AiSettings`, not secrets.json); at request time, and when the settings UI needs to show status, Fleet calls `claude auth status` (and the Codex equivalent) fresh rather than caching a status flag, and `claude -p`/`codex exec` are trusted to handle their own already-established login entirely internally — matching OpenClaw's own stated principle ("Claude owns the login and token refresh lifecycle") almost verbatim. _Alternative considered_: cache a "last known status" purely for instant UI paint on tab-open — rejected because a cached value can only ever be a stale hint (the user can log out from a terminal at any time) and the source doc's own principle (§3.4) is explicit that Fleet should not shadow state the CLI already owns correctly; `get_ai_settings` already re-reads persona warnings fresh on every call, so re-checking CLI status on the same cadence is consistent with existing precedent, not a new one.

**Disclosure keys on (provider, auth method), not provider alone — and lives on `AiSettings`, not on `ProviderProfile` itself.** `disclosure_acknowledged` moves from one bool per provider-settings struct to `AiSettings.acknowledged_disclosures: Vec<ProfileKey>`, checked via `AiSettings::disclosure_acknowledged(key)`. Switching Anthropic from API key to subscription shows its own, differently-worded disclosure. _Alternative considered, tried first and reverted_: a `disclosure_acknowledged` field directly on `ProviderProfile` — this was the original design and was implemented, but caught in review before shipping: `disable_profile` removes a profile from `enabled_profiles` entirely, which would silently discard that field along with it, so re-enabling the same (provider, auth method) later would wrongly ask again — directly contradicting this capability's own "Disclosure does not repeat once acknowledged" scenario (which explicitly covers a disable/re-enable cycle, not just switching away and back while staying enabled). Tracking acknowledgment as its own list, independent of profile presence, is what actually satisfies that scenario: the fact "the user was told X" doesn't become untrue just because a profile was toggled off. _Alternative considered_: one acknowledgment per provider brand regardless of auth method, since data leaves the device to the same company either way — rejected because the source doc's §8.2 explicitly treats "which credential/account is used" as a materially different fact from "data leaves the device," and API-key-usage-based billing vs. a personal subscription login are different enough consequences to warrant separate, accurately-worded consent.

**Fleet triggers CLI login as best effort; detection of an already-logged-in CLI is the hard requirement.** `claude auth status` (and the Codex equivalent) is proven to work cleanly when spawned with piped stdio, no TTY — verified live this session. Actually driving `claude auth login`/`codex login` (browser redirect + local callback listener) from a headless-spawned child process was deliberately not tested, to avoid disrupting the developer's real, live authenticated session. Stage 2 therefore treats "detect and use an already-authenticated CLI" as the thing that must work, and "Fleet can trigger the login flow itself" as best-effort with a documented fallback (tell the user to run the CLI's login command themselves in a terminal, then refresh in Fleet's settings).

**OpenAI/Codex subscription support ships as explicitly experimental.** Unlike Anthropic's path, it could not be manually verified — no ChatGPT/Codex subscription was available. It's included anyway (not deferred to a later change) because the "equal priority" auth-method work in the proposal is about the data model and settings UI supporting either provider's subscription auth uniformly, and half-supporting that (data model ready, UI ready, but only one of two providers wired up) would leave the profile-list UI showing a capability that silently doesn't exist for OpenAI. The experimental flag is `ProviderProfile::is_experimental()` (a profile-level fact in `settings.rs`, not an `AiProvider` trait method — the settings UI can check it without constructing a provider), which is what keeps this honest rather than silently equivalent to the verified Anthropic path.

**Codex's two confirmed transport gaps get worked around, not hidden.** No incremental text (only one complete `item.completed`/`agent_message` per turn): `Codex::chat()` still delivers it as a paced sequence of `StreamChunk`s (reusing `Mock`'s own `chunk_text`) rather than one block, satisfying the `ai-provider` "Streaming responses" requirement's _user-visible_ behavior honestly labeled as synthesized pacing, not real incremental generation (see that requirement's own new scenario for this case). No system-prompt flag: the persona is written to a temp file and passed via `-c model_instructions_file=<path>`, the same mechanism OpenClaw itself uses — real and documented, but its precedence relative to a project's own `AGENTS.md`/`AGENTS.override.md` in the invocation's working directory isn't confirmed by documentation alone (see Risks). _Alternative considered for the system prompt_: prepend the persona into the single prompt argument instead of using `model_instructions_file` — rejected in favor of matching OpenClaw's own approach once it was found to exist, since a real documented mechanism (even with unconfirmed precedence in edge cases) is preferable to a user-message-level workaround with no precedent.

**Codex gets the same warm-session model as Claude, not an accepted asymmetry.** `codex exec resume <SESSION_ID>` is confirmed to exist, so `Codex` tracks its own session id (Codex calls it `thread_id`) in an `Arc<Mutex<Option<String>>>` exposed via the same `session_id()` shape as `ClaudeCodeCli`, with the same stale-resume-retries-fresh fallback. The "maybe Codex doesn't support this, and that's an acceptable named asymmetry" framing from an earlier pass of this document is superseded now that the capability is confirmed to exist — not exercising it would have been giving up a real optimization for no reason, once it was known to be available.

**`ClaudeCodeCli::list_models()` returns a curated alias list, not an empty one.** There is no live model-listing endpoint for a CLI the way there is for an HTTP API, so the "Live model listing" requirement's original "fetched live rather than hardcoded" rule can't apply to this implementation literally — but returning an empty list (as a first pass did, following `Mock`'s precedent) silently left the settings UI with no way to pick a model at all for this one profile, inconsistent with every other configurable profile. Fixed by returning Claude Code's own known `--model` aliases: `sonnet`, `opus`, `fable`, `haiku` (an earlier pass excluded `haiku` on the mistaken read that `claude --help`'s "e.g. 'fable', 'opus', or 'sonnet'" was an exhaustive list rather than an illustrative one — it isn't; `haiku` is confirmed valid, visible in Claude Code's own `/model` picker). _Alternative considered_: leave it empty and let the UI hide the model picker entirely for this profile — rejected as a worse, silent inconsistency than a small, known-good list; a user who wants a specific Claude model tier should be able to pick one the same way they can for every other profile.

**New `ProviderError` variants: `RuntimeUnavailable`, `SubscriptionExpired`, `QuotaExhausted`.** Added to the existing `{Network, Auth, RateLimited, InvalidResponse, Cancelled}`. `Auth` is reused (not replaced) for "not logged in yet," parallel to its existing "wrong API key" meaning. `RateLimited` and `QuotaExhausted` are kept distinct because they call for different user-facing guidance: one says "retry shortly," the other says "wait for the next billing period" — collapsing them would make the settings UI give the wrong advice for one of the two cases.

**Migration auto-converts the existing single provider into one API-key profile.** Every Stage 1 config's provider was necessarily API-key auth (subscription auth didn't exist), so there is no ambiguity to resolve — `active_provider: Some(kind)` plus that kind's existing settings becomes exactly one `ProviderProfile { provider: kind, auth_method: ApiKey, model }`, set as the default profile, with its Stage 1 `disclosure_acknowledged` value (if any) carried into the new `acknowledged_disclosures` list. _Alternative considered_: reset to zero profiles and force re-configuration — rejected as needless friction for something fully derivable, and inconsistent with `AiSettings::sanitize`'s existing degrade-gracefully-don't-discard philosophy.

**Conversation / Execution / External Runtime Session: a typing-only boundary, added after grilling a source-doc addition made mid-implementation.** The source doc added a requirement to distinguish three concepts Fleet was at risk of conflating as Stage 3's Agent Core approaches: `Conversation` (the user-visible chat container), `Execution` (one turn's run), and `External Runtime Session` (a CLI-backed provider's own session state). Grounding this against the actual code already built in this change found that two of the three already exist in substance, just unnamed: the chat log session (`chat_log_store.rs`, identified by a `PathBuf` whose filename embeds a random id) _is_ a Conversation; `ChatRuntimeState.cli_sessions: HashMap<ProfileKey, String>` (added in this change's own Group 4) _is_ an External Runtime Session reference map, just untyped. `Execution` is the one genuinely new concept — today a "turn" is only the `send_chat_message` -> `run_generation` call chain, with no id and no per-turn recorded state beyond one global `PendingGeneration`.

Resolved scope, from grilling this directly against the source doc's own "define the boundary, not the engine" instruction:

- New `crates/fleet-snowfluff/src/session_domain.rs` (app crate, not `fleet-snowfluff-ai` -- these are Fleet-product concepts per the source doc's own "Fleet product layer" framing, and `fleet-snowfluff-ai`'s whole point is depending on nothing project-specific): `ConversationId`, `ExecutionId`, `ExternalSessionRef`.
- `ConversationId` is derived from the session file's path through one narrow function (`ConversationId::from_session_path`), not independently generated and stored -- nothing today needs to reference a conversation before its log file exists or after it's been moved, so a stored, path-independent id would be solving a problem that doesn't exist yet. Kept behind one function specifically so that if this changes later, it's a one-place edit, not a search-and-replace.
- `ExternalSessionRef` is a bare `struct ExternalSessionRef(pub String)`, no internal runtime tag -- `cli_sessions`'s map key already disambiguates which (conversation, profile) a ref belongs to, so a second, redundant tag on the value could only ever drift from the key, never add information.
- `ExecutionId` is generated fresh per `send_chat_message` call and threaded through `run_generation` as a plain value -- not persisted, not added to `ChatEvent`/`ChatStateSnapshot`, since nothing on the frontend needs per-execution visibility yet and nothing regresses by it still not having it.
- `PendingGeneration`'s shape (`ChatRuntimeState.pending: Mutex<Option<PendingGeneration>>`, one global slot) is explicitly _not_ touched. _Alternative considered_: give it an `execution_id` and reshape `pending` into a map now, on the same "cheap now, expensive later" reasoning used elsewhere in this change (e.g. `enabled_profiles`) -- rejected because that reasoning doesn't transfer: `enabled_profiles`'s shape is a _persisted config file format_ real users would need migrating twice; `PendingGeneration` is pure in-memory runtime state with no persistence and no external contract, so reshaping it later costs the same as reshaping it now. There is also, today, no concurrency design to build the map's real shape around -- Stage 3 hasn't decided what "multiple concurrent executions" even means yet (parallel tool calls? sub-agents? something else?), so guessing at the map's shape now risks getting it wrong in a way that _does_ need a second pass, unlike leaving it alone.
- `ChatRuntimeState.cli_sessions` **is** re-keyed now, from `ProfileKey` alone to `(ConversationId, ProfileKey)`, despite being argued from the same "only one conversation exists today" starting point as `PendingGeneration`. The two are not actually symmetric: `PendingGeneration` staying a single slot is a _can't-do-this-yet_ limitation, loud and obvious the moment it matters. `cli_sessions` staying keyed by `ProfileKey` alone would be a _silent wrong-answer_ risk the moment Fleet ever has two concurrent conversations -- one conversation's Claude session handed to another conversation's request for the same profile, with no error, just a session-continuity bug that would be hard to notice and harder to trace back to its cause. Closing off a whole class of future silent-correctness bug is worth the two extra characters in a `HashMap` key; guessing at a concurrency shape nobody has designed yet is not.
- No spec delta for this slice: nothing about it is user-observable (the chat window behaves identically; `--resume` still works exactly as Groups 2-3 built and verified it, just keyed more precisely internally) -- OpenSpec's own rule is that specs describe behavior, and none changed. If Stage 3 later gives `Execution` real, observable status/tool-trace, that requirement belongs to whatever change ships Stage 3's Agent Core, not this one.
- Landed inside this change rather than as a separate one, on the user's explicit call -- the source doc itself frames this as riding alongside subscription-first chat under the same Stage 2 heading ("Subscription-first Chat **+ Session Domain Foundation**"), not as an independent initiative.

## Risks / Trade-offs

- **[Risk]** OpenAI/Codex subscription support is unverified end-to-end. Two specific, now-concrete versions of this: (1) `model_instructions_file`'s precedence relative to a project's own `AGENTS.md`/`AGENTS.override.md` is not confirmed — if an `AGENTS.md` in the invocation's working directory wins, the persona could be silently ignored in favor of Codex's own default coding-assistant identity; (2) `--sandbox read-only` prevents shell _execution_, but doesn't confirm the model won't still narrate or propose tool use in its reply text, which would read oddly for a desktop-pet chat reply. → **Mitigation**: shipped as explicitly experimental (`ProviderProfile::is_experimental()` + settings-UI marking); tasks.md includes a real behavioral check as soon as a tester with a ChatGPT/Codex subscription is available, before the experimental marking is ever removed.
- **[Risk]** Codex's synthesized streaming (chunking one complete response after the fact) means the _entire_ reply latency happens before the user sees anything, unlike every other provider where partial text appears while the model is still generating — a Codex reply will feel like a longer pause followed by a faster-than-real "typing" catch-up, not genuinely progressive. → **Mitigation**: accepted as an inherent, disclosed limitation of this transport (see the "Streaming responses" requirement's new scenario) rather than something to hide; the alternative (no chunking at all, one instantaneous block) would be a worse and less consistent user experience, not a more honest one.
- **[Risk]** The temporary `model_instructions_file` written per `Codex::chat()` call is deleted after the stream completes, but an aborted generation (`stop_generation`'s `handle.abort()`, a hard cancellation) can skip that cleanup code, leaking a small file into the OS temp directory. → **Mitigation**: accepted — low severity (a small, per-call markdown file, not a growing or sensitive artifact), and the OS temp directory already gets cleaned up independently of Fleet; a more robust fix (e.g. a `Drop` guard) is not worth the complexity for this failure mode.
- **[Risk]** Headless (no-TTY, piped-stdio) `claude auth login` / `codex login`, triggered by Fleet as a spawned subprocess, might not complete correctly — only `auth status` (a read) was verified this way, not `auth login` (an interactive-feeling browser-redirect flow). → **Mitigation**: documented fallback — if Fleet-triggered login doesn't complete cleanly, the settings UI instructs the user to run the CLI's login command themselves in a terminal and then refresh; "detect an already-logged-in CLI" (which is verified) remains fully functional regardless of how login was performed.
- **[Risk]** Even with `--strict-mcp-config --setting-sources ""`, `claude -p` carries real baseline overhead per fresh session (~2.8K cache-creation input tokens measured live for a one-sentence reply) beyond what a lean, direct API call would cost — this consumes the subscription's own rate-limit window (5-hour/weekly rolling caps on Pro/Max) faster than a hypothetical minimal integration would, for chatty, casual desktop-pet conversation. → **Mitigation**: the warm/resumed-session design is exactly this risk's mitigation — only the first turn of a Fleet chat session pays full cost; every resumed turn is a cache-read. Not eliminated, bounded.
- **[Risk]** A resumed Claude-CLI session can go stale or invalid (the CLI's own local session store was pruned, compacted, or the session simply doesn't exist anymore) between one Fleet message and the next. → **Mitigation**: a failed `--resume` is expected to surface as a CLI-level error on that call; `ClaudeCodeCli` treats it as "start a fresh session" (clear the stored session id, retry once without `--resume`) rather than a hard failure — the user loses that session's cache-read discount and any conversational memory Claude's own CLI held, but not the ability to keep chatting; Fleet's own JSONL log is unaffected either way since it was never the thing relying on the CLI's memory.
- **[Risk]** A fresh Claude-CLI session (first use in a Fleet chat session, or after a stale-resume fallback) does not see earlier turns from a _different_ provider used earlier in the same Fleet chat session, unlike every other `AiProvider` implementation, which always gets the full reconstructed context window regardless of which provider handled earlier turns. → **Mitigation**: accepted for this change — provider-switching mid-conversation isn't a primary use case Stage 2 optimizes for (Task Routing/Fallback, which would make this common, is explicitly out of scope), and the alternative (replaying reconstructed history into a fresh Claude-CLI session as its first message) would partly defeat the "don't resend everything" cost benefit that motivates resuming at all.
- **[Risk]** The profile-list data model is real surface area (four call sites: `build_provider`, `set_active_provider`/its replacement, `acknowledge_provider_disclosure`, `chat_commands.rs`'s active-provider read) touched for a feature whose actual routing logic doesn't ship until a later change — this change's user-visible payoff is smaller than its migration cost. → **Mitigation**: accepted deliberately (Question 4 in discovery) specifically to avoid a second data-model migration when Stage 3 routing logic lands; the alternative (minimal `auth_method`-only change now) was considered and rejected for that reason.
- **[Risk]** Depending on the `codex` CLI as a new runtime dependency for a capability whose completion bar is already lowered (experimental) risks the change looking done when its riskiest path isn't. → **Mitigation**: the "Experimental provider marking" requirement makes this a spec-level, testable guarantee (it must be visibly labeled), not just a note in this document that could be forgotten during implementation.

## Migration Plan

On first load after this change, `AiSettings::sanitize` (or its replacement) detects the old shape (`active_provider` present, no `enabled_profiles` field) and converts it in place: one `ProviderProfile` from the previous `active_provider` + that provider's settings sub-struct, set as `default_profile`, written back in the new shape on next save. A config with neither shape (fresh install) yields zero enabled profiles, matching the existing "no provider configured by default" guarantee. No user action, no re-disclosure, no data loss. Rollback: none needed beyond the usual "new capability behind existing gates" — a user who never enables a subscription auth method sees no behavior change beyond the settings UI's new profile-list layout.
