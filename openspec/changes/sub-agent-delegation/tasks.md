Verify with a test: two overlapping `confirm_via_popup` calls (second started before the first resolves) both eventually resolve with their own, correct responses — neither is silently dropped.
- [ ] 1.2 Update `get_pending_tool_confirmations`/`resolve_tool_confirmations` and the confirmation window's open/close logic to operate on the front of the queue, advancing to the next batch (if any) once the current one resolves, keeping the window open across batches rather than closing between them. Verify by reading the code and a test on the queue-draining sequence: resolving one batch while another is queued leaves the window open and the UI shows the next batch.

## 2. General bounded concurrent tool-call execution

- [ ] 2.1 Change the `Auto`-tier dispatch inside `AemeathAgentRuntime::run()`'s per-call loop from sequential `.await` to bounded concurrent execution via `futures_util::stream::iter(...).buffer_unordered(MAX_CONCURRENT_TOOL_CALLS)` (new constant, default 3), collecting each call's result into a slot indexed by its original position in `calls`, then pushing to `messages`/`trace` in that original order — never in completion order. Verify with tests: multiple `Auto`-tier calls in one turn, where an artificially-delayed call is requested first but finishes last, still has its result appear before the other calls' results in `messages` (request order preserved despite completion order); more calls in one turn than `MAX_CONCURRENT_TOOL_CALLS` all still execute exactly once each, none dropped, only throttled in how many start at once.
- [ ] 2.2 Verify (read the code, and with a test) that a turn with only one `Auto`-tier or `Confirm`-tier call behaves identically to before this change — same final text, same messages, same trace — confirming this is a behavior-preserving change for the common single-call case.

## 4. The `delegate_task` capability and its special-cased dispatch

- [ ] 4.1 Add a `delegate_task` `ToolDefinition` (reserved name constant, e.g. `DELEGATE_TOOL_NAME = "delegate_task"`; description explaining the capability and, per design.md Decision 1/proposal, instructing the model to call it multiple times in one turn for independent sub-tasks rather than one at a time; `{"task": {"type": "string"}}` required-string schema). Verify with a test that the definition's `parameters` is valid tool-call JSON schema and its `name` matches the reserved constant dispatch will check against.
- [ ] 4.2 Add a way to build a registry excluding one named tool (e.g. `ToolRegistry::without(&self, name: &str) -> ToolRegistry`), used to build a delegated child's own registry (parent's tools minus `delegate_task`, enforcing the depth-1 cap structurally). Verify with a test that the filtered registry's `definitions()` excludes the named tool and `find()` cannot locate it, while every other tool is still present and unchanged.
- [ ] 4.3 Inside `AemeathAgentRuntime::run()`'s per-call dispatch, add a branch recognizing `call.name == DELEGATE_TOOL_NAME` _before_ the generic `registry.find()` path: parse `{task: string}` from the call's arguments (malformed arguments or a missing `task` field follow the existing `Rejected` path, unchanged); build the child's message list (the system prompt from Group 3, plus the task as a single user message — no parent history, no persona); build the child's registry via `without(DELEGATE_TOOL_NAME)` (Group 4.2); recurse with `self.run(provider, child_messages, &child_registry, ctx, permission, &mut |_: &str| {}).await` — a no-op `on_text_delta`, never the parent's own. No manual `Box::pin` wrapping needed at the call site: `run` is an `#[async_trait::async_trait]` method, so it already returns `Pin<Box<dyn Future<...> + Send>>` — the macro boxes its body for every call, including this recursive one. Map `Ok(AgentOutcome { text, .. })` to `ToolResult::ok(text)` and `ToolOutcome::Executed { ok: true }`; map `Err(_)` to a model-visible error result and `ToolOutcome::Executed { ok: false }` — both folded into the parent's own `messages`/`trace` exactly like any other `Auto`-tier call. Verify with tests: a delegated call's child completes and its final text appears as the tool's result in the parent's `messages`, with a matching `Executed { ok: true }` trace entry; a child's own registry (built via 4.2) has no `delegate_task` entry, so a child that attempts to delegate gets the same "unknown tool" rejection an ordinary unknown-tool call would; a child's own narration, pushed through its no-op `on_text_delta`, never reaches any value the test can observe reaching the parent's real callback; a child that errors (e.g. hits its own `MaxIterationsReached`) produces `Executed { ok: false }` with a model-readable error message, not a parent-level failure.
- [ ] 4.4 Confirm `delegate_task` itself never requires confirmation — it is dispatched before the `Auto`/`Confirm`/`Deny` tier branches are reached, so no `required_permission` check ever applies to it directly (only to whatever tools the _child_ calls, which still go through the normal tiers). Verify with a test exercising a `delegate_task` call directly, confirming no `PendingConfirmationItem` is ever produced for the delegation call itself, matching design.md's Decision 3.
