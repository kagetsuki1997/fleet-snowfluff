## 2. General bounded concurrent tool-call execution

- [x] 2.1 Change the `Auto`-tier dispatch inside `AemeathAgentRuntime::run()`'s per-call loop from sequential `.await` to bounded concurrent execution via `futures_util::stream::iter(...).buffer_unordered(MAX_CONCURRENT_TOOL_CALLS)` (new constant, default 3), collecting each call's result into a slot indexed by its original position in `calls`, then pushing to `messages`/`trace` in that original order — never in completion order. Verify with tests: multiple `Auto`-tier calls in one turn, where an artificially-delayed call is requested first but finishes last, still has its result appear before the other calls' results in `messages` (request order preserved despite completion order); more calls in one turn than `MAX_CONCURRENT_TOOL_CALLS` all still execute exactly once each, none dropped, only throttled in how many start at once. Restructured the per-call loop into three passes: a synchronous `CallPlan` classification pass (unchanged logic, just deferred execution for `Auto`), a concurrent `Auto`-tier execution pass (`buffer_unordered`, results written into a `Vec<Option<(bool, String)>>` slot indexed by original position), and an ordered writeback pass reading `calls`/`plans`/slots together. **Found and fixed while implementing**: a closure returning `impl Future` fed into `.filter_map()` hit rustc's HRTB inference limit (cannot unify the borrowed-`call` lifetime across every closure invocation) — fixed by building `Vec<Pin<Box<dyn Future<...> + Send>>>` via a plain `for` loop instead of a closure, giving `stream::iter` one concrete item type. Used a `Notify`-gated pair of test tools (`WaitsForGate`/`SignalsGate`) rather than real-time sleeps for the completion-order test, so it's deterministic, not flaky. 2 new tests.

Landed exactly as specified. 1 test.
- [x] 4.3 Inside `AemeathAgentRuntime::run()`'s per-call dispatch, add a branch recognizing `call.name == DELEGATE_TOOL_NAME` _before_ the generic `registry.find()` path: parse `{task: string}` from the call's arguments (malformed arguments or a missing `task` field follow the existing `Rejected` path, unchanged); build the child's message list (the system prompt from Group 3, plus the task as a single user message — no parent history, no persona); build the child's registry via `without(DELEGATE_TOOL_NAME)` (Group 4.2); recurse with `self.run(provider, child_messages, &child_registry, ctx, permission, &mut |_: &str| {}).await` — a no-op `on_text_delta`, never the parent's own. No manual `Box::pin` wrapping needed at the call site: `run` is an `#[async_trait::async_trait]` method, so it already returns `Pin<Box<dyn Future<...> + Send>>` — the macro boxes its body for every call, including this recursive one. Map `Ok(AgentOutcome { text, .. })` to `ToolResult::ok(text)` and `ToolOutcome::Executed { ok: true }`; map `Err(_)` to a model-visible error result and `ToolOutcome::Executed { ok: false }` — both folded into the parent's own `messages`/`trace` exactly like any other `Auto`-tier call. Verify with tests: a delegated call's child completes and its final text appears as the tool's result in the parent's `messages`, with a matching `Executed { ok: true }` trace entry; a child's own registry (built via 4.2) has no `delegate_task` entry, so a child that attempts to delegate gets the same "unknown tool" rejection an ordinary unknown-tool call would; a child's own narration, pushed through its no-op `on_text_delta`, never reaches any value the test can observe reaching the parent's real callback; a child that errors (e.g. hits its own `MaxIterationsReached`) produces `Executed { ok: false }` with a model-readable error message, not a parent-level failure. **Landed with one correction to how the depth-1 cap is actually enforced**: the classification pass calls `registry.find(&call.name)` _first_, for every call, _then_ checks whether the found tool's name is `DELEGATE_TOOL_NAME` — not a bare name-equality check performed before any registry lookup. This matters for correctness, not just style: a bare name check would let a delegated child's own hallucinated `delegate_task` call (its registry built via `.without(DELEGATE_TOOL_NAME)`, so the name genuinely isn't offered to it) still be treated as real delegation, defeating the depth-1 cap entirely. Checking the registry first means a child's own hallucinated call correctly falls through to the ordinary `UnknownTool` rejection instead. `Delegate(String)` is a new `CallPlan` variant carrying the already-parsed task, sharing the _same_ concurrent-execution pass as `Auto` (both push a `(usize, bool, String)`-producing future into the same `auto_futures`/`buffer_unordered` pool, so several delegations in one turn share the same `MAX_CONCURRENT_TOOL_CALLS` bound as every other tool, not a separate limit) and the _same_ writeback arm (`CallPlan::Auto(_) | CallPlan::Delegate(_)`) — a tighter unification than the task's own wording implies, which fell out naturally once both were expressed as the same `(index, ok, content)` tuple shape. 4 integration tests covering: a successful delegation's result reaching the parent's `messages`/`trace`; a child's hallucinated `delegate_task` call rejected as unknown (depth-1 proof); a child's narration never reaching the parent's real `on_text_delta` (via a shared `Arc<Mutex<String>>` accumulator that only ever sees the parent's own text); a child that exhausts its own `max_iterations` (sharing `self.max_iterations` with the parent, so both need ≥2 for this scenario) reporting `Executed { ok: false }` to the parent rather than failing the parent's own `Result`. One self-caught bug during implementation: an earlier draft of the iteration-exhaustion test used `max_iterations: 1`, which starves the _parent_ of its own second turn too (same shared runtime) — fixed to `max_iterations: 2` with the child's own two turns both kept non-terminating.
