## Context

See `proposal.md` for motivation and scope. This design covers only the consuming direction (Aemeath as MCP client); the server/hosting direction is explicitly deferred (see proposal's own Why).

Two existing pieces this design builds directly on top of, read and verified during exploration rather than assumed:

- `Tool`'s trait shape (`agent_tool.rs`): `definition()`, `required_permission(args, ctx)`, `allows_session_remember()`, `execute(args, ctx) -> Result<ToolResult, ToolError>`, where `ctx: &ToolContext` is just `{ project_root, conversation_id }` — no `AppHandle`.
- `delegate_task`'s own precedent for a capability that needs more than `Tool::execute()` can reach: special-cased by name in dispatch, with a stub `Tool` impl whose `execute()` is unreachable in correct operation, existing only so the model can discover it via `definitions()`.
- `cli_process.rs`'s `kill_on_drop(true)` pattern for Claude Code/Codex: confirmed (by reading it) to spawn a _fresh_ subprocess per chat turn, not a persistent one — it works only because those CLIs have their own session-resume concept. MCP has no equivalent, so this precedent does not transfer to connection lifecycle (see Decisions).
- `ai_commands.rs`'s `trigger_login`/`check_profile_status`: confirmed to be pure fire-and-forget-plus-poll, never touching a token directly — works only because the `claude`/`codex` binaries own their entire OAuth dance internally. An arbitrary third-party MCP server has no such companion CLI, so this _UX shape_ (don't block, let the user come back, make "ready?" a cheap repeatable check) is reused, but the plumbing underneath it is new: Fleet Snowfluff itself has to be the OAuth client this time.

The MCP authorization flow design below follows the protocol's own spec (`modelcontextprotocol.io/specification/2025-06-18/basic/authorization`), verified directly rather than assumed, including: `initialize`/`tools/list` as fixed protocol methods every compliant server implements identically; OAuth need discovered via a `401` + `WWW-Authenticate` header pointing to `/.well-known/oauth-protected-resource`, never declared upfront; stdio transport explicitly directed by the spec to use environment-supplied credentials instead of this OAuth flow at all; Dynamic Client Registration (RFC 7591) as the mechanism that makes "connect to anything, no pre-registered allowlist" actually work for OAuth-protected servers.

## Goals / Non-Goals

**Goals:**

- Let the model connect to a third-party MCP server from a plain chat request, with no pre-vetted list constraining what it can resolve to, gated by an explicit confirmation of the concrete, resolved command/URL.
- Make a connected server's tools indistinguishable from native tools to `AemeathAgentRuntime::run()`'s own dispatch.
- Support both transports MCP actually uses in practice (stdio, HTTP/SSE) and both credential shapes the spec itself distinguishes (env-var for stdio, OAuth for HTTP).

**Non-Goals:**

- Aemeath as an MCP _server_ (Reading B / "Aemeath-owned capability" exposed to Claude Code/Codex/OpenClaw) — no consumer for it yet; see proposal's Why.
- Per-tool permission granularity or include/exclude tool filtering at connect time (OpenClaw's own model does this; deliberately deferred — see Risks).
- Calling a provider's own OAuth token-revocation endpoint on server removal — local deletion only.
- Proactive connection health-checking or keepalive — lazy reconnect on next use only.
- A curated/known-server list of any kind, even as a non-binding resolution aid — the model resolves purely from the request and its own knowledge.

## Decisions

**`connect_mcp_server` is special-cased _inside_ `AgentRuntime::run()`'s own per-iteration dispatch, exactly like `delegate_task` — not before it reaches `run()` at all, which was an error in earlier framing (caught during review, before any code was written to match the wrong version).** The model decides to call `connect_mcp_server` the same way it decides to call any other tool — mid-turn, inside an already-running `run()` call, reading the model's own streamed tool-call request. There is no point _before_ `run()` starts where that decision could have been made yet, so there is nothing to intercept "one layer up."

What _is_ true, and was the real point buried in that wrong framing: this needs a _different_ kind of capability-threading than `delegate_task` needed, not a smaller amount of it. `delegate_task` only ever needed `provider`/`registry`/`permission`/`ctx` — all things `run()` already carries as its own parameters for normal operation, so recursing into itself was free. `connect_mcp_server` needs `AppHandle`-level things (opening a browser, writing settings, showing the real confirmation popup) that none of those carry, and that `agent_runtime.rs` has no way to reach — confirmed by checking `Cargo.toml`: zero `tauri` dependency in that crate, a deliberate, existing boundary this design must not break by threading a literal `AppHandle` through `ToolContext` or `run()`'s own signature.

Two ways to resolve this without breaking that boundary were weighed; the user chose the first:

- **Chosen: mirror `PermissionDecider`'s own existing shape.** A new trait — `McpConnector` — defined abstractly in `fleet-snowfluff-ai` (no `tauri` dependency in the trait itself):

  ```rust
  #[async_trait::async_trait]
  pub trait McpConnector: Send + Sync {
      async fn connect(&self, request: McpConnectRequest) -> McpConnectOutcome;
  }
  ```

  Implemented concretely (with a real `AppHandle`, doing the actual popup + connection work) in the app crate, the same way `PopupPermissionDecider` implements `PermissionDecider` today. Passed into `run()` as a new parameter, `mcp_connector: &dyn McpConnector`, the same way `permission: &dyn PermissionDecider` already is. `connect()`'s own implementation must itself resolve three cases, not block indifferently: await the confirm-popup decision (fast), await the actual connection attempt when no OAuth is needed (one round trip), but _never_ await OAuth completion — for that case it starts the browser flow and returns a `Pending` outcome immediately, matching the spec's own "does not block the rest of the conversation" scenario. `run()`'s internal dispatch itself needs no new control-flow concept for this — it awaits `mcp_connector.connect(...)` in place, exactly as it already awaits `permission.decide(...)` for any other `Confirm`-tier call.

  This does add a parameter to `run()`'s already-six-parameter signature (already carrying `#[allow(clippy::too_many_arguments)]`), and the two call sites that never actually need it — the recursive `delegate_task` call inside `run()` itself, and `mix-mode-local-tools`'s own continuation call — must still pass _something_. Both pass a trivial, never-actually-reached implementation mirroring `AlwaysDenyConfirm`'s own existing shape: harmless because `connect_mcp_server` is excluded from both of those paths' registries (same exclusion `delegate_task` itself already gets for the recursive case; see proposal's "What Changes" and 4.6), so the real implementation is never invoked from either.

  _Rejected: bubbling it up instead of reaching sideways_ — `run()` returning a new outcome/error variant signaling "paused, needs `connect_mcp_server` handled," with the caller doing the real work and resuming via a fresh `run()` call fed the updated message list. Workable (and its own blast radius turned out smaller than first assumed, since only `run_generation_with_tools`'s call site would ever see it), but it introduces a genuinely new "stop the loop, do side effects, restart with different inputs" control-flow shape — this codebase's closest precedent (`mix-mode-local-tools`'s hand-rolled first iteration) only works because `run()` hadn't started yet at that point, which doesn't hold here since the pause can happen at any iteration. It would also give the resumed call a fresh `max_iterations` budget each time, letting repeated `connect_mcp_server` calls stretch one turn across more total iterations than the limit is meant to allow. The chosen option avoids both of these by not stopping the loop at all.

A stub `Tool` impl still exists purely for `definitions()` discovery, mirroring `DelegateTool`'s own unreachable-`execute()` shape. **This is unaffected by, and does not affect, the Settings-UI "add manually" path (5.2) or the removal/refresh-tools commands (4.4/4.5)** — those are plain `#[tauri::command]`s invoked directly from the frontend, which already receive `AppHandle` the normal way; they never go through `AgentRuntime::run()`'s dispatch at all. Only the chat-triggered path is affected.

**No curated server list, by explicit choice, not oversight.** Considered and rejected: constraining resolution to a known/vetted registry (closer to a "marketplace" model). Rejected because the user's own concrete motivating case included connecting to a custom local service nobody could have pre-vetted, and because the `Confirm` popup showing the exact resolved command/URL already provides the real safety boundary — the same bar `run_command` already clears, not a lower one. The cost accepted: a vague request ("connect the GitHub MCP server") may get resolved to a stale or wrong invocation from the model's own training data; the user catches that at the confirmation step, same as they would catch a wrong `run_command` invocation today.

**Credential shape forks by transport, following the MCP spec's own directive, not an independent choice.** The spec explicitly says stdio implementations "should not" follow its OAuth authorization spec and should instead take credentials from the environment. So: stdio gets a plain text field for an env-var value, injected at spawn time, no pending state (either the user has the value or they don't — no asynchronous step to wait for). HTTP gets the full OAuth dance: on-demand local redirect listener (started right before opening the browser, exits on success or timeout — chosen over an always-running listener since there's no benefit to a permanently-open local port waiting for a callback that might never come), PKCE (no client secret, standard for native/desktop OAuth clients per OAuth 2.1), plus a manual "paste the code" fallback for environments where a loopback redirect won't work (borrowed from OpenClaw's own `mcp login --code` fallback, confirmed via reading OpenClaw's official docs at `docs.openclaw.ai/tools/mcp.md`). Both end up in `secrets_store`.

**Connections are eager once, at add time; lazy (reconnect-on-next-use) after that — these are not the same policy applied twice.** The _first_ connection has to be eager and synchronous: it is the only point where `initialize`/`tools/list` can run to validate the server actually works and produce something to cache for the settings-UI tools browser. Every connection _after_ that (app restart, a connection that died mid-session) is lazy: reconnected only when a registry build actually needs it, never proactively monitored. A new `McpConnectionState` (Tauri-managed singleton, same tier as `ChatRuntimeState`/`ToolConfirmationState`) holds live connections keyed by server id, looked up — and lazily (re)established if missing — every time a registry is built. This is new: unlike `cli_process.rs`'s per-turn-fresh-spawn precedent (confirmed not to transfer — MCP has no session-resume concept to make respawning per-call cheap), the underlying connection genuinely has to outlive any single attempt or conversation.

Cross-checked against Claude Code's own actual behavior (verified via web search, not assumed): it reconnects _every_ configured MCP server as its own subprocess on _every_ launch, and new sessions block until all of them connect or time out — a well-documented pain point, with multiple open feature requests asking for lazy/on-demand initialization instead. This design's "eager once at add time, lazy reconnect after" deliberately avoids that failure mode: reconnection cost is paid only for a server a given session actually ends up using, not for every connected server on every app start.

**Removal diverges from `disable_profile`'s own precedent, on purpose.** Read `disable_profile` (`ai_commands.rs:166-177`): it only removes a profile from `enabled_profiles`, never touches the stored credential in `secrets_store` — fine for a user-typed API key with no live session concept. An OAuth grant is a live thing a remote service is actively honoring; leaving it behind after the user believes they've "removed" the server is a real lingering risk, not inert leftover data. So removal here does a hard local delete of the stored credential immediately. Calling the provider's own revocation endpoint (RFC 7009) would be more thorough but adds real complexity (discovering each provider's revoke endpoint, handling its own failure modes) for marginal benefit — a user who wants that can revoke from the provider's own account settings today, the same as they would for a leaked API key.

**Permission default: blanket per-server `Confirm`, not per-tool.** MCP carries no risk-tier metadata of its own — Fleet Snowfluff cannot know whether a given discovered tool is safe without running it. OpenClaw's own model (confirmed via reading its docs) does per-tool include/exclude filtering and per-tool "Allow Always" grants; deliberately not matched here for v1, reusing the _existing_ session-remember (`RememberKey`) mechanism as the escape hatch instead of building a new filter UI from scratch. Worth revisiting if a server with many tools, only some of which are actually risky, turns out to be a common real case — not assumed up front.

**A newly connected server's tools are available starting the next message, never live mid-turn.** Matches `mix-mode-local-tools`'s own established reasoning for the identical question: the registry is built once per attempt and handed around as an immutable reference for that whole call; mutating it mid-loop would be new, nontrivial machinery for a benefit (using a tool in the same turn that connected it) nobody has asked for.

## Risks / Trade-offs

- **No per-tool filtering means a server with one genuinely risky tool among many benign ones still makes the user confirm the risky one individually at call time (fine) but offers no way to pre-emptively hide it.** → Accepted for v1; `Confirm`-tier enforcement still catches the risky call itself, this only affects convenience, not safety. Revisit if OpenClaw-style filtering turns out to be worth the UI surface once real usage shows it's needed.
- **A vague chat-resolved connection request can resolve to a stale or wrong command if the model's training knowledge about a given public MCP server is out of date.** → Mitigated, not eliminated, by the mandatory confirmation step showing the resolved command before anything runs. A user who doesn't recognize what a correct invocation _should_ look like could still approve a wrong one — the same residual risk `run_command`'s own `Confirm` tier already carries today for any tool call, not a new category.
- **Lazy reconnect with no health-checking means a dead connection is only discovered when something actually tries to use it, surfacing as a failed tool call rather than a proactive warning.** → Accepted; matches this project's general preference for the simplest thing that works over speculative monitoring infrastructure.
- **Dynamic Client Registration (RFC 7591) is not universally supported by every OAuth authorization server, and the "no curated list" decision depends on it working for a given server to avoid needing a pre-registered client ID.** → For a server whose authorization server doesn't support it, the spec's own fallback is manual registration; this surfaces to the user as a clear error naming that specific limitation, not a silent failure — not solved, just not hidden.
- **A remote MCP server receiving tool-call arguments and results is a third-party data flow distinct from the existing cloud-LLM-provider disclosure the settings UI already shows.** → The connect-time confirmation (showing the resolved URL before connecting) is treated as covering this for v1, rather than building a second, separate disclosure-acknowledgment flow alongside the existing cloud-provider one. Worth revisiting if real usage shows users don't register a remote MCP server as meaningfully different from a local one just from seeing its URL once.
