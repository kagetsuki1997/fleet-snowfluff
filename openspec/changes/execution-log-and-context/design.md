## Context

See `proposal.md` for motivation. The relevant current state, confirmed against the code:

- `ContextManager`/`SessionLog` exist (`fleet-snowfluff-ai/src/context_manager.rs`) but are never called: `chat_commands.rs` builds every prompt via `prompt::assemble_messages(persona, language, &context, &message)` directly, and appends every reply via `chat_log_store::append_entry` directly. `build_context` currently takes `(session_path, persona, language, user_message) -> Vec<Message>`; `record_execution` takes `(session_path, reply: &str)`.
- `AgentRuntime::run` returns `Result<String, AgentError>` — only the final text. Inside the loop body, every tool call resolves one of five ways (unknown tool name, malformed arguments, `Auto`-tier executed, `Deny`-tier refused, `Confirm`-tier approved-then-executed or declined), each pushing a `Message::tool_result(...)` into the loop's own local `messages: Vec<Message>`, which is dropped when `run` returns.
- The CLI session sidecar is `cli_session_store.rs`: `StoredSession { profile, session_id, cwd, seen_turns }`, one entry per profile, loaded with `load`/`usable` and overwritten with `upsert`. `ChatRuntimeState::{stored_session, cli_context, record_session}` in `chat_commands.rs` are the only callers, backed by an in-memory `cli_sessions` cache that's a cache _in front of_ this file (a miss reads the sidecar; every store writes through).
- `new_chat_session` aborts any pending generation, clears `cli_sessions`/`remembered_tools`/unread, then points `chat_state.session_path` at a freshly created file. `stop_generation` only aborts the task — `tokio::task::JoinHandle::abort()` causes the task to be dropped at its next `.await` point; code after that point in the task's own body never runs, so the task cannot itself write a "this was cancelled" record on the way out.
- `ChatStateSnapshot` (returned by `get_chat_state`) does not expose `session_path` to the frontend today.
- Nothing enumerates past conversations; `chat_log_store::find_latest_session` only ever finds the single most recent one.

## Goals / Non-Goals

**Goals:**

- Every attempt to produce a reply — including a discarded `mix`-mode local attempt — is recorded as an `Execution`, uniformly, with enough detail to answer "what actually happened" after the fact.
- A turn's tool activity is available to the next turn's context, regardless of which profile answers it.
- The CLI-session "latest per profile" view is derived from the execution record instead of a separate, overwritten-in-place file.
- A user can see, reopen, and delete past conversations.
- `ContextManager` is actually wired into the chat flow for the first time.

**Non-Goals:**

- Extracting facts/decisions/artifacts, or any `ConversationContext` summary/compaction — left to Stage 7, same reasoning as before (needs a decision about who does the extraction, which this change doesn't need to make).
- Sub-agent fields (`parent_execution_id`, `ExecutionKind`) — Stage 5's job, added additively on top of this change's `Execution` shape later.
- Deleting or otherwise managing an external CLI runtime's own session store (Claude Code's `~/.claude/projects/...`, Codex's equivalent). Aemeath never owned that lifecycle and this change does not start.
- A conversation index file for fast listing — a directory scan is used instead (see Decision 7).
- Renaming, pinning, or any other conversation-list management beyond open and delete.
- Letting more than one generation be in flight across different conversations — the existing single-global-`PendingGeneration` invariant is unchanged; opening a past conversation cancels, it does not parallelize.

## Decisions

**1. `AgentRuntime::run` returns `AgentOutcome { text, trace }`, not just `String`.** `AgentOutcome` is a plain struct; `trace: Vec<ToolInvocation>` where `ToolInvocation { name: String, outcome: ToolOutcome }` and:

```rust
enum ToolOutcome {
    Executed { ok: bool },
    DeniedByPolicy,
    DeclinedByUser,
    Rejected { arguments: Value }, // capped in size, see Decision 2
}
```

This is purely additive to information the loop already computes at each of its five push sites — no new permission logic, no change to what gets executed or how `on_text_delta` streams. `DeniedByPolicy` (a `Deny`-tier tool) and `DeclinedByUser` (a `Confirm`-tier tool the user said no to this time) are kept distinct because they point at different places to look later: one is a standing setting, the other is a one-off choice that might go differently next time. `Rejected` covers both the unknown-tool-name and malformed-arguments cases, which the loop today already treats identically (both produce an error tool-result with no execution attempted). Alternative considered: a callback parameter (`on_tool_call: &mut dyn FnMut(...)`) parallel to `on_text_delta` — rejected because a trace is consumed once, at the end, by a caller that isn't reacting live the way the UI reacts to streamed text; a typed return is simpler to extend later (Stage 5 will want the same shape for a sub-agent's result) than a growing parameter list.

**2. Only `Rejected`'s arguments are retained, and capped.** Every other outcome (`Executed`, `DeniedByPolicy`, `DeclinedByUser`) keeps neither the call's arguments nor its result past the turn — consistent with the existing stance that tool content (file contents, command output) shouldn't be duplicated into a second persisted location. `Rejected` is the exception: the call never reached `execute()`, so there is no tool-side content to protect, and the argument itself is the only available diagnostic for "why did the model's call not parse." Capped at a fixed size (reusing `run_command`'s/`read_file`'s existing `20 KB`-class constant, or a dedicated one of comparable size), truncated the same way those two already do (cut on a UTF-8 boundary, with a visible marker) — not because a malformed-arguments blob is a realistic attack surface for a desktop pet app, but because every other model-originated value already persisted in this codebase is bounded, and this is the one new place that persists one.

**3. The execution log is `<ts>_<id>.executions.jsonl`, append-only, two lines per Execution.** Named and placed exactly like the sidecar it replaces (`chat_log_store`'s date-folder convention), but append-only rather than overwritten-in-place, because an append-only log is what makes the start/end split — and therefore cancellation detection (Decision 5) — possible at all. A `start` line is written before the provider is called; an `end` line is written on completion, error, or (via the RAII guard) cancellation. Both lines share the Execution's id so they can be paired on read. Alternative considered: extend `.sessions.json` in place with route/status/trace fields — rejected because it reintroduces exactly the "latest only, history discarded" shape this change exists to replace, and has nowhere to represent an orphaned `start` from a crash (an in-place file only ever holds "the current state," never "what happened").

**4. `.sessions.json` is deleted outright; the "latest usable session per profile" view is derived by scanning the execution log.** No second, cached file kept in sync with the execution log — two files that can disagree is the same problem this change is retiring. The derivation (scan for the latest `end` with a matching profile, an external session reference present, and a matching working directory — status `Completed` or `Errored` both qualify, since the existing code already persists and resumes a session captured right before a stream error, confirmed at `store_cli_session_id`'s error-path call in `run_generation`; `Escalated` is excluded, since the one route that can ever end `Escalated` (`MixLocal`, the local Ollama attempt) never has an external session reference to begin with — Ollama has no resumable-session concept) is cheap at this app's realistic log sizes, and degrades the same way a corrupt sidecar already did: a line that fails to parse is skipped (matching `log::parse_log`'s existing behavior for the transcript), worst case falling back to a fresh, history-seeded session — a fallback this app already relies on for the ordinary stale-resume case. `cli_session_store.rs` is removed; a new `execution_log_store.rs` provides the append/scan functions, and `ChatRuntimeState::{stored_session, cli_context, record_session}` are rewritten against it, keeping their existing signatures and the in-memory `cli_sessions` cache as-is (it was already a cache in front of persisted state; which persisted state it's in front of changes, not its own shape or its `new_chat_session`-clears-it lifecycle).

**5. Cancellation (and a crash) is recorded via an RAII guard, not from `stop_generation` itself.** `tokio::task::JoinHandle::abort()` drops the task at its next await point; the task's own code never resumes to write anything after that. A guard constructed at the start of each of the four `run_generation*` functions writes the `start` record in its constructor, exposes `mark_completed(...)`/`mark_errored(...)` to be called right before the function's own normal return, and writes the `end` record from `Drop::drop` using whatever was last set — defaulting to `Cancelled` if nothing was. `Drop::drop` is synchronous, so the write is a blocking `std::fs` call, matching the existing pattern of every other persistence function in this codebase (`chat_log_store::append_entry`, the old `cli_session_store::upsert`) being plain synchronous file I/O already, never `async fn`. This covers Stop and an unexpected process exit uniformly, with no second code path for "did Stop get pressed" versus "did something else kill this" — both look identical (a guard dropped without being told it finished), which is fine, since recovering from either looks the same (seed the next session fresh). Alternative considered: have `stop_generation` write the record itself — rejected because it only covers the one cancellation path that goes through that command, leaving any other future way a generation could end abruptly unrecorded by default rather than covered by default.

**6. `ContextManager` reads the execution log itself, through a new `ExecutionLog` trait beside the existing `SessionLog`, not merged into it.** Parallel shape (`read(&self, session_path) -> Vec<ExecutionRecord>` / `append(&self, session_path, event: &ExecutionEvent)`), implemented in the app crate (`execution_log_store`) for the same reason `SessionLog` is — path resolution needs `AppHandle`, which `fleet-snowfluff-ai` must not depend on. Kept as a second trait rather than one combined `ConversationStore` because the two are different formats with different lifetimes read by the same component for the same `session_path`, but a future reader (Stage 7 compaction, say) may legitimately want only one; a merged trait would force it to depend on both. `build_context` is reshaped to read the immediately preceding `Execution` for the conversation and, if it made any tool calls, render a short note (same style as `history_preamble`'s existing "catch-up" rendering for CLI sessions) prepended into the assembled messages. `record_execution` is extended to also append the just-completed turn's `Execution` end record — note that by Decision 5, the _start_ record and most of the _end_ record's fields are already written by the `ExecutionRecorder` guard at the `chat_commands.rs` level, so `ContextManager.record_execution`'s own job here is narrower than `build_context`'s: it appends the transcript-facing reply text, exactly as `AemeathContextManager::record_execution` already does today, plus whatever of the `Execution` end record isn't already covered by the guard. Deciding _whether the next turn gets a tool-activity note_ is entirely `build_context`'s responsibility, on the next call, not something `record_execution` decides in advance — the two are separate reads of the same persisted `Execution`, at different times, for different purposes.

**7. Conversation listing is a directory scan, not an index file.** `chat-logs/*/*.jsonl`, first line's content (truncated) as a title, last line's timestamp (or file mtime, whichever is cheaper to obtain reliably) as recency, sorted newest-first, unbounded, no pagination. Given this is a single-user desktop app with a realistically small number of small log files, scanning is unmeasurably fast and adds no new failure mode (no index to go stale against a manually deleted file, nothing new to update on every `append_entry`). Revisit only if real log volume ever makes this perceptibly slow, with evidence.

**8. `open_conversation(path)` and `delete_conversation(path) -> bool` are new, separate commands.** `open_conversation` shares a private helper with `new_chat_session` for the "abort pending, clear unread, clear remembered tools" part; only the "what path to point at" step differs (a freshly created path vs. a caller-supplied existing one) — matching this file's existing convention of one command per intent rather than an overloaded signature with a mode flag. `delete_conversation` returns `false` (refused) when `path` matches the currently-open conversation — checked directly against `chat_state.session_path`, no separate "is this the open one" query command, matching how `enable_profile` already signals refusal by return value rather than a pre-check round trip. `ChatStateSnapshot` gains the current `session_path` so the picker can label/grey out the open conversation using data it already has to fetch anyway (it does not need a dedicated query for this). Deleting removes both the transcript and the execution log file for that conversation, best-effort (`.ok()` on each, matching every other file-removal/write in this codebase); it never touches an external CLI runtime's own session store, per the standing "Aemeath doesn't own that lifecycle" principle already established by `cli-session-continuity`'s own design.

## Risks / Trade-offs

- [The `AgentRuntime::run` signature change is a breaking change to a trait with one real implementation and one call site, but several test doubles] → mechanical to update; no behavioral change to tool execution or permission enforcement, only to what's returned afterward.
- [Recording every turn, including discarded `mix`-mode attempts, roughly doubles write volume on the execution-log file for an escalating turn] → each write is one small JSON line; negligible at this app's scale.
- [The RAII guard's `Drop` impl must do blocking file I/O inside an async task's drop glue] → already the pattern for every other persistence call in this codebase; no new async-in-drop hazard introduced.
- [A conversation whose old `.sessions.json` predates this change loses its stored CLI session reference] → explicitly accepted in the proposal as the one breaking-format change; degrades to the already-handled stale-resume-fallback path (fresh, history-seeded session), not a failure.
- [Directory-scan listing could become slow at very large log counts] → accepted now, revisit later only with real evidence (Decision 7).
- [Deleting a conversation that referenced a CLI session leaves that session alive in the CLI's own store, unreachable from Aemeath afterward] → deliberate; matches the existing "never reach into an external runtime's own lifecycle" stance, not an oversight.

## Migration Plan

No data migration. On first run after upgrade, any existing `.sessions.json` sidecar is simply no longer read (and may be deleted by a one-time cleanup pass, or left as an orphaned file — implementation detail, not a behavior difference either way); every conversation that had one falls back to a fresh, history-seeded CLI session on its next message to that profile, identical in observable behavior to today's stale-resume path. No existing chat log (`.jsonl`) is touched. Rollback is reverting the change; a `.executions.jsonl` file left behind by a newer build is simply ignored by an older one (it never reads that filename).
