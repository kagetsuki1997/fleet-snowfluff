## Goals / Non-Goals

**Goals:**

- A task-routing mode (`single`/`mix`) that lets a local Ollama profile handle simple messages, with the default profile as both the complex-task destination and the fallback.
- Tool calling for the Ollama profile specifically, via a new provider capability, plus an agent loop, permission model, and 4 native tools built against it.
- A by-case native-tool allow-list for Claude Code/Codex, replacing the current blanket deny, so those CLIs' own read-only tools (including their first-party web search) work without Aemeath reimplementing anything.

**Non-Goals** (see `proposal.md` - Capabilities and `docs/fleet-snowfluff-feature-planning.md` §13's Stage boundaries for where each of these actually lands):

- Tool calling for `OpenAiCompatible`/`Anthropic` (API-key) profiles — named fast-follow, not in this change, because each provider's streamed tool-call wire format is independent, real parsing work.
- Sub-agent/Delegation (Stage 5), Capability Escalation + External Runtime Sessions (Stage 4), MCP (Stage 6), Context Awareness's active-window/idle-time/clipboard signals (Stage 6), Context Engine's compaction/memory-retrieval upgrade (Stage 7).
- `TaskRequirements` is defined as a domain type but not consumed by this change's routing decision — reserved for a future capability-escalation change.
- Live, per-invocation confirmation for Claude Code/Codex's own native tools.

## Decisions

**Naming: `Aemeath`, not `Fleet`, for every new short-name identifier.** The product's full name (`Fleet Snowfluff`) and existing crate names (`fleet-snowfluff*`) are unaffected — only new component/runtime-style names introduced by this change (`AemeathAgentRuntime`, Aemeath Tool Registry, etc.) use the new prefix, per the user's explicit direction this session.

**Task Router `mode` is a new `AiSettings` field, default `Single`, exactly preserving today's behavior until changed.** `single` routes every message to `default_profile`, unchanged from `subscription-first-chat`. `mix` tries the enabled Ollama profile first. See `docs/fleet-snowfluff-feature-planning.md` §4.13 for the full mechanism.

**`TaskRouter::route()` is called exactly once per message, to produce the _initial_ `ExecutionRoute` — it is not called again when that attempt is escalated or fails.** This resolves a gap found during review: Group 1's domain types (`TaskRouter`, `RoutingContext`, `ExecutionRoute`) must not be defined and then left unused by the concrete `mode` mechanism. `send_chat_message` builds a `RoutingContext` and calls `TaskRouter::route()`, which resolves to `default_profile` for `single` mode always, and for `mix` mode to the enabled Ollama profile if one exists, or to `default_profile` directly if it doesn't (that's knowable upfront from settings, not a runtime failure, so it belongs in the initial route, not the fallback path). Everything that happens _after_ that — the local model's own escalation-marker response, or an infra-level failure mid-attempt — is handled by the execution layer redirecting to `default_profile` directly, without a second call to `TaskRouter::route()`. This mirrors a boundary the planning doc already draws for session resumption (§4.6: "真正的 create / resume / terminate 必須由 Runtime Adapter / SessionManager 完成" — the Router's job ends at producing the route; retries are the Runtime's job) and keeps "Task Routing" and "Fallback" as the two distinct mechanisms §4.8 already separates (its own fallback-trigger list is infra-only — auth/quota/rate-limit/error/unavailable — never "the model decided it's complex," which is exactly the new case this change introduces at the execution layer, not the Router layer). `ExecutionRoute` does not need a "might redirect later" concept added to it to accommodate this.

**Mix-mode classification happens inside the local model's own first response, not as a separate pre-pass.** _Alternatives considered and rejected_: (1) keyword/rule-based scoring against `TaskRequirements` flags — rejected because it reintroduces the "complexity score" pattern §4.2/§0-principle-12 explicitly argue against, and needs a separate phrase list per one of Aemeath's 5 UI locales; (2) asking the local model to classify via a dedicated pre-pass request — rejected because it adds a full extra model round-trip to every message before the real work even starts. The chosen approach — the local model's entire reply is the literal token `<<ESCALATE>>` when it judges the message complex, detected via incremental prefix-matching against the streamed reply rather than waiting for the full marker length — means the common (simple) case diverges from `<`/`<<` on its first character and pays almost no extra latency, while the rare (complex) case pays one short round-trip before `default_profile` starts. `personas/task-router-rules.md` (user-authored, loaded via `include_str!` — same pattern as `persona::BUNDLED_DEFAULT_PERSONA_YAML` — and appended to the local call's system prompt the same way `persona_store::load()` loads `personas/aemeath.yaml`, but never appended to `default_profile`'s own call) carries both the judgment criteria *and* the reply-format contract itself (plain persona reply for a `LOCAL` decision, exactly `<<ESCALATE>>` for an `ESCALATE` decision) — the file is the single source of truth for both concerns, with no separate code-owned preamble layered on top of it.

**`run_generation` is restructured to buffer-then-decide for the local attempt in mix mode.** Before forwarding anything to the UI, it compares the accumulating buffer against `<<ESCALATE>>` character-by-character: a mismatch at any position is a conclusive "simple," flushes the buffered prefix immediately, and continues forwarding the rest of the stream exactly as today; a full match discards everything buffered (never shown, never logged) and re-dispatches the same message to `default_profile` with the plain persona-only message list. The same discard-and-redispatch path also fires on infra-level failure (Ollama disabled, `RuntimeUnavailable`, mid-stream error) — both converge on one `default_profile` retry. Only the winning attempt is ever appended to the chat log.

**`ToolCallingProvider` is a separate trait from `AiProvider`, not an extension of `chat()`.** _Alternative considered_: extend `ChatStream`'s item type to an enum (`TextDelta`/`ToolCallRequest`) and thread tool definitions through `chat()` universally — rejected because it would touch all six existing providers, including `ClaudeCodeCli`/`Codex`, which must never receive Aemeath's own tool definitions (they own their native tool loops entirely; see the External CLI native-tool access control requirement instead). The chosen shape — `async fn chat_with_tools(&self, messages: Vec<Message>, tools: Vec<ToolDefinition>) -> Result<ToolCallStream, ProviderError>` on a new `ToolCallingProvider: AiProvider` trait — is additive and opt-in per provider. Whether a given profile is tool-capable is decided inside `build_provider()`'s existing match arms at construction time (returning a `RoutedExecution` enum: `PlainChat(Box<dyn AiProvider>)` vs `ToolCapable(Box<dyn ToolCallingProvider>)`), not via `Box<dyn AiProvider>` downcasting, since the concrete type is already known at that point and Rust has no clean way to ask a type-erased trait object whether it also implements a second trait. **v1 implements `ToolCallingProvider` for `Ollama` only** — `OpenAiCompatible`'s fragmented `delta.tool_calls[].function.arguments` streaming and `Anthropic`'s `tool_use`/`input_json_delta` content blocks are each independent, real parsing work, deliberately deferred.

**`AgentRuntime::run` streams every iteration's text live via a callback, rather than buffering until the whole tool-calling loop finishes.** Found as a real gap while wiring the Agent Loop into `chat_commands.rs` (task 6.1): `run`'s original signature only returned `Result<String, AgentError>` once the loop ended, unlike every other chat path's real-time `ChatEvent::Chunk` streaming. _Alternative considered_: accept buffered-until-done delivery for tool-calling turns as a known UX difference — rejected as an unforced regression with a cheap fix available. Chosen shape: `run` takes an added `on_text_delta: &mut (dyn for<'a> FnMut(&'a str) + Send)` parameter, invoked for every `ToolCallStreamItem::TextDelta` on *every* iteration (not only the final one) — a model that narrates before calling a tool still streams that narration live, exactly as if the tool call never happened, since only tool-call JSON and tool execution stay invisible. The explicit `for<'a>` HRTB is required, not stylistic — the natural elided `&str` form fails to compile under `#[async_trait]`'s macro expansion, which binds it to the same fixed lifetime as the method's other reference parameters instead of a fresh per-call one (confirmed via the actual compiler error, not assumed). `run_generation_with_tools` (`chat_commands.rs`) forwards the callback straight to `channel.send(ChatEvent::Chunk{..})` and `partial_text`, identical in shape to `stream_to_completion`'s existing streaming.

**Tool-calling is wired in at a message's *final* destination profile only — never inside `run_generation_mix_local`'s own local-classification attempt.** `mix` mode's local-first attempt is a separate, text-only mechanism (`task-router-rules.md` appended, watching for `<<ESCALATE>>` via prefix-matching); giving it tools too would mean deciding what an in-progress tool call means for that detection (e.g. a first action that's a tool call rather than text produces no bytes to sniff at all). Combining the two is real, separate design work, not resolved here — `route_provider`-based tool-calling only applies where a profile is already the final, settled destination: `send_chat_message`'s direct-to-`default_profile` branch (covers `single` mode always, and `mix` mode when Ollama isn't enabled) and `run_generation_fallback` (mix-mode's escalate/infra-failure destination). A user who wants tool-calling behavior today sets Ollama as their `default_profile` directly rather than relying on `mix` mode's local attempt to have it.

**A second, real bug surfaced by the same wiring work, fixed in the same pass**: `routed_to_local`'s check (`route.profile_key == local_profile_key`) ignored `task_router_mode` entirely. Since `single` mode always resolves to `default_profile`, a user who sets *Ollama* as their `default_profile` (a normal, unrestricted choice) would trigger the mix-mode local-classification dance even in `single` mode, which is supposed to mean "always use `default_profile` directly, no routing games". Fixed by gating on `task_router_mode == Mix` as well, not just profile-key equality.

**The `PermissionDecider` wired in for task 6.1 denies every `Confirm`-tier call outright (`DenyAllConfirm`).** A deliberate, explicitly-labeled placeholder, not a design decision — the real popup-backed decider is tasks 6.2-6.4. `Auto`-tier tools already work end to end; anything needing confirmation reports back to the model as "not permitted to run" until then, never silently auto-approved.

**Ollama's `chat_with_tools` reuses `think: false`, the same as plain chat — this is not an oversight, it's required.** `providers/ollama.rs`'s existing `build_chat_body` already sets `"think": false` because a thinking-capable model was found (live, this project) to silently consume its entire `num_predict` budget on invisible reasoning, producing an empty reply for a short persona chat turn. It would be reasonable to assume tool-calling wants the opposite — that reasoning helps pick the right tool and arguments — but that assumption is wrong here: [ollama/ollama#10976](https://github.com/ollama/ollama/issues/10976) documents that `think: true` combined with tool definitions currently produces **empty output entirely** for Qwen3 models in Ollama, independent of budget size. `chat_with_tools` therefore keeps `think: false`, for a second, stronger, and separately-documented reason than the plain-chat case, not because it was left unexamined. `parse_ndjson_line` (the existing plain-chat NDJSON parser) only deserializes `message.content`/`done` and would silently drop a `tool_calls` field if one appeared in a response line — `chat_with_tools` needs its own parsing function, not an extension of the existing one.

**Claude Code/Codex native-tool access is a by-case allow-list, not blanket deny, and explicitly not a live-confirm system.** Replaces `DISALLOWED_TOOLS` with a per-profile setting built into `--allowedTools`/`--disallowedTools` at spawn time. Default: `Read`/`Glob`/`Grep`/`WebSearch`/`WebFetch` = auto; `Write`/`Edit`/`Bash`/`NotebookEdit`/`Task`/`SlashCommand` = deny, user-adjustable. `WebSearch`/`WebFetch` moved into auto this session after confirming Claude Code's `WebSearch` is Anthropic's own first-party server-side tool (`web_search_20250305`) bundled into the same subscription/API session already in use — no separate key, no extra cost, read-only, same risk tier as `Read`/`Glob`/`Grep`. `--permission-mode manual`/`dontAsk` exist but are unverified for headless/no-TTY spawning, and the current spawn already closes stdin — so `confirm` degrades to `deny` for these CLI-owned tools rather than claiming a live-approval channel that hasn't been shown to work. Codex's own by-case granularity is unverified/experimental (not installed to check directly); its sandbox tiers are probably coarser than Claude's per-tool list.

**`Tool` trait has an args-aware `required_permission`, not a static per-tool-name table, and needs no `AppHandle`.** `read_file`/`list_directory`'s permission tier depends on the requested path (inside vs. outside the configured project directory), not just tool identity, so the check takes `&Value`/`&ToolContext`. All popup/window/oneshot orchestration lives in the agent loop's own calling code, not inside `Tool::execute()` — kept out deliberately so `Tool` implementations stay as portable/testable as `AiProvider` already is, with nothing Tauri-specific leaking in.

```rust
trait Tool {
    fn definition(&self) -> ToolDefinition;
    fn required_permission(&self, args: &Value, ctx: &ToolContext) -> PermissionTier;
    fn allows_session_remember(&self) -> bool { false }
    async fn execute(&self, args: Value, ctx: &ToolContext) -> Result<ToolResult, ToolError>;
}
struct ToolContext { project_root: Option<PathBuf>, conversation_id: ConversationId }
struct ToolResult { content: String, is_error: bool }
```

**Tool-confirmation is a new Tauri window, batched per turn, resolved via `oneshot`.** New window label `"tool-confirmation"`, same `WebviewWindowBuilder`/`index.html`-reuse/label-branching pattern as `status_bubble.rs`, but `focused(true)` (unlike the bubble's deliberate `focused(false)`) since the user must actively respond. Every `Confirm`-tier tool call from one model turn is collected and shown in a single popup (not sequential), with per-item accept/deny plus approve-all/deny-all shortcuts; one `oneshot::Sender`/`Receiver` pair blocks the agent-loop task until the user responds or closes the window (closing = treated as deny). **No new state is needed on the chat window or status bubble** — `ChatRuntimeState.pending` already stays `Some(...)` for the whole duration the task is blocked on the oneshot, so `get_chat_state`'s existing `is_pending`/`partial_text` and the bubble's `...` glyph are already correct; this also composes for free with the existing single-generation-at-a-time rule.

**Session-remember is keyed by `(ConversationId, ToolName)` for path-less tools, but `(ConversationId, ToolName, path)` for `read_file`/`list_directory`.** Remembering by tool name alone for the two path-aware tools would silently re-trust every future path for the rest of the session, defeating the project-directory boundary entirely. `allows_session_remember()` returns `false` for `run_command`/write-capable tools (one approved command shouldn't blanket-trust future ones with a wildly different risk profile) and `true` for read-only tools. Stored in-memory only on `ChatRuntimeState`, never persisted, cleared by `new_chat_session` on the same lifecycle as `cli_sessions`.

**`read_file`/`list_directory`: the configured project directory is an auto-zone, not a hard boundary — anything outside it escalates to confirmation instead of being refused outright.** A new `AiSettings.project_root: Option<PathBuf>` (global, not per-conversation — Aemeath has exactly one conversation at a time today). A requested path is auto-allowed only if it canonicalizes to somewhere inside `project_root` (real canonicalization + containment check, not a string-prefix check, closing `..`-traversal and symlink-escape holes); everything else — including every request when `project_root` is unset, since an empty root has nothing "inside" it — goes through the confirmation popup showing the actual path. `run_command`'s working directory, by contrast, is hard-pinned to `project_root` with no popup-based escalation to a different directory, since shell execution is a meaningfully higher risk tier than read-only file access.

**`run_command`: bounded, non-streaming, and must not leak orphaned processes on cancel.** `sh -c` (Unix) / `cmd /C` (Windows), `stdin(Stdio::null())`, `tokio::time::timeout` at 30s (kills the child and returns a clear timeout result rather than hanging), stdout/stderr captured separately plus exit code, combined output capped at ~20KB with a truncation marker. No incremental output streaming to the chat UI — it runs silently under the same pending state as everything else and returns one complete result. **The spawned `tokio::process::Child` must set `.kill_on_drop(true)`** — `stop_generation`'s existing `pending.handle.abort()` is a hard task-abort, and `tokio::process::Child` does not kill its child on drop by default, so without this an aborted `run_command` would leave the subprocess running as an orphan.

**`web_search` serves only the Ollama tool-calling path — it is not a general Aemeath search feature.** Claude Code/Codex already get real, first-party search for free via the native-tool allow-list decision above. Brave Search API was researched and ruled out — its free tier was discontinued as of ~February 2026, now requiring a credit card even for the metered-credit plan.

**`web_search` is a three-tier, no-key, no-login fallback, in this order: a locally-run `ddgs api` server, then a public SearXNG instance, then the official DuckDuckGo Instant Answer API.** Originally shipped two-tier (SearXNG → DuckDuckGo, see the Risks section below for how both degraded in practice after ship). Following a user report that DuckDuckGo's Instant Answer API can't serve non-English queries (it's Wikipedia-fathead-sourced and heavily English-biased by nature — see the Risks entry on this), the `ddgs` PyPI package (successor to `duckduckgo_search`) was evaluated and adopted as the new first tier: `ddgs api` (its own documented default, `127.0.0.1:4479`) runs a local FastAPI wrapper around `ddgs`'s own multi-backend search (rotating across DuckDuckGo/Google/Bing/Brave/Yahoo/Mojeek server-side), confirmed live to return real, genuinely non-English-capable ranked results — the whole reason for adopting it. It is **entirely optional**: nothing in this tool requires it to be installed, and a user who never runs `ddgs api` sees no behavior change from the original two-tier design, since a connection failure falls straight through to SearXNG exactly as before. Availability is cached with a 60s cooldown after a failure (`DdgsCooldownState`) so a search doesn't pay a fresh connection-refused round trip on every call while it isn't running (the common case), while still noticing fairly soon if the user starts it mid-session — deliberately not a permanent/forever cache, since `ddgs api` is user-managed local infrastructure that can start or stop at any point in the app's lifetime, unlike the fixed public endpoints the other two tiers hit. A successful-but-empty `ddgs` response (its own `backend=auto` selection is observed to intermittently pick a rate-limited upstream and return nothing for a single call) falls through to SearXNG/DuckDuckGo exactly like an outright failure does — the multi-tier design is itself the retry mechanism, so `fetch_ddgs` makes exactly one attempt, no internal retry loop.

**`get_system_context` ships a deliberately narrow slice, not §9's full Context Awareness.** New `sysinfo` dependency for CPU/memory/uptime, plus already-available `chrono` for date/time and `std::env::consts::OS`. Explicitly excludes active-window title, idle time, and clipboard content — confirmed via direct codebase search that none of that infrastructure exists yet, and each has a real, already-documented platform gap (no Wayland API for active-window, macOS needs accessibility permission for it, idle-time needs its own crate, clipboard is privacy-sensitive and meant to default off) that belongs to Stage 6's proper build, not a narrower Stage 3 stand-in.

**Native-CLI binary discovery (`agent-core-and-task-router` Group 10) resolves an absolute path before every `claude`/`codex` spawn, rather than trusting a bare `Command::new(name)`'s own PATH search.** Found as a real bug (user-reported, not discovered during design): launched outside a terminal — Finder/Dock on macOS, a `.desktop` file on Linux — Aemeath inherits a minimal `PATH` that never sees Homebrew/nvm/volta/fnm/Nix's shell-rc-sourced additions, so both CLI providers silently report "not installed" even when they are. Windows is the exception: its `PATH` is a persistent registry value Explorer rebuilds each new process's environment from, so a freshly-launched process is normally fine; the one real Windows failure mode is a *stale* one (an installer added itself to `PATH` while Explorer was already running, and Explorer won't see it until it restarts). New `providers/cli_locator.rs`, shared by both `ClaudeCodeCli` and `Codex`, resolves and memoizes (per binary name, process lifetime) an absolute path via, in order: (1) this process's own `PATH` — on Windows, merged with a fresh read of `HKCU\Environment\Path`/the machine-wide `...\Environment\Path` straight from the registry via the already-present `winreg` dependency, sidestepping the stale-Explorer-session problem directly rather than trusting the possibly-stale inherited value; (2) a small curated list of common per-OS install locations (`/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin` on macOS; those plus `~/.nix-profile/bin`/`/run/current-system/sw/bin`/`/etc/profiles/per-user/<user>/bin` on other Unix; `%APPDATA%\npm`, `~\scoop\shims`, chocolatey's bin dir on Windows); (3) Unix only, the user's own login shell's actually-resolved `PATH`, captured once by spawning `$SHELL -ilc` and reading it back (bounded by a 5s timeout). Step 3 is deliberately the one mechanism that generalizes across Homebrew, nvm/volta/fnm, *and* Nix without hardcoding an install-manager-specific path table — it just asks the shell that already knows the right answer, which matters specifically for NixOS: there is no stable, guessable install location to add to step 2's static list (every package lives under a content-hashed `/nix/store/<hash>-.../bin`), so step 2's Nix-specific entries are only the stable *profile-symlink* locations, and step 3 is what actually finds a Nix-installed CLI in the common case. If nothing is found, `resolve()` returns the bare name unchanged, so a genuinely-missing CLI still fails exactly as it did before this module existed.

## Risks / Trade-offs

- **[Risk]** Mix-mode escalation depends on the local model reliably following the "reply with only `<<ESCALATE>>`" instruction. A model that prepends stray text or occasionally fails to follow it either shows a slightly-off response to the user (if it should have escalated but didn't) or silently costs one extra `default_profile` call (if it escalates when it shouldn't have) — both failure directions are recoverable, neither corrupts state or fails the turn. → **Mitigation**: detection uses prefix-matching, not exact-string equality, and the two failure directions are asymmetric in a safe way (the worse one is "slightly lower answer quality," not "broken conversation").
- **[Risk]** `run_generation`'s restructuring for buffer-then-decide is a real behavior change to a well-exercised code path (`single` mode and every existing provider path must be unaffected). → **Mitigation**: the buffering/decision logic is scoped to the `mix`-mode local-attempt branch only; `single` mode's call path is untouched.
- **[Risk]** A public SearXNG instance has no SLA and can disappear, rate-limit, or block Aemeath's traffic without notice. **Confirmed materialized, not just theoretical**: live-checked against `searx.be` plus roughly a dozen other commonly-listed public instances (post-ship, in response to a user report) — every one currently returns either an anti-bot JS-proof-of-work/CAPTCHA challenge page (served as `200 OK` HTML instead of JSON, unaffected by a real browser `User-Agent`) or an HTTP `429`. This is not a header/User-Agent problem — that class of challenge can only be defeated by executing JavaScript, which no HTTP client here does — and DuckDuckGo's Instant Answer API was independently confirmed *not* to be failing for the same reason: it answers correctly (its narrow, by-design "infoboxes/definitions/disambiguation only" scope was mistaken for a failure — see the "Just Another Test" placeholder response any non-entity query gets, which this tool's parser already ignores by only reading `AbstractText`/`Heading`/`RelatedTopics`, never `meta`). → **Mitigation**: unchanged in substance — the honest "no results" terminal state already handles this without any user-visible error — but a real desktop `User-Agent` was added to the shared `reqwest::Client` as baseline hygiene (won't defeat the JS-challenge tier, may avoid simpler UA-sniffing blocks elsewhere), and 3 new `#[ignore]`d live tests in `web_search.rs` (`live_searxng_reports_its_current_reachability_and_parse_result`, two `live_duckduckgo_...` tests) let this be re-checked by hand going forward without re-deriving the investigation. No hardcoded multi-instance SearXNG fallback list was added — the ecosystem-wide gating observed makes that unlikely to help right now, and would trade a small, well-understood risk surface for an unbounded one (which instances, in what order, re-verified how often).
- **[Risk]** DuckDuckGo's Instant Answer API cannot serve non-English queries in practice — its dataset is Wikipedia-fathead-sourced and heavily English-biased, not a language-detection block (an ordinary English how-to query fares no better, confirmed live — see the SearXNG risk entry above). Three alternatives were investigated (Bing's HTML search — looked anti-scraping-gated from testing infrastructure; Yahoo's HTML search — real non-English results but an unresolved, inconsistently-reproducible transport-level connection reset that a real attempt at fixing (forcing HTTP/1.1, a bounded retry) did not reliably solve; Parallel Search — a real API, but always requires an API key/signup even on its free tier, failing this tool's "no credential required" requirement) before `ddgs` (see the Decision above) was adopted instead. → **Mitigation**: resolved by adopting `ddgs api` as the new first tier — see the Decision above and its own Risk entry below for the tradeoff that came with it.
- **[Risk]** The new `ddgs` tier depends on local infrastructure (`ddgs api`, `127.0.0.1:4479`) the user must separately install and run themselves — a real dependency this tool otherwise has none of (SearXNG/DuckDuckGo need nothing installed). A user who never sets it up simply never benefits from it, with no behavior change from the original two-tier design; a user who does gets meaningfully better, genuinely multilingual results, but only while `ddgs api` happens to be running. → **Mitigation**: entirely optional by construction (a connection failure falls straight through to SearXNG, exactly as before this tier existed), a 60s failure cooldown (`DdgsCooldownState`) keeps the cost of it being absent to one failed connection attempt per minute rather than per search, and nothing about this tier is mentioned in this tool's own description shown to the model (`WebSearchTool::definition()`) — the model has no expectation of it either way, so its absence is never a surprising capability gap from the model's perspective, only ever a quality difference in the results it gets back.
- **[Risk]** `ddgs`'s own `backend=auto` selection intermittently returns zero results for a single call even when the server is genuinely reachable and working (observed live, both with `auto` and with several explicit `backend=` values tried by hand — consistent with individual upstream engines it rotates through being themselves intermittently rate-limited, not a bug in `ddgs` or in this code). → **Mitigation**: `search()`'s existing multi-tier fallback already absorbs this — an empty `ddgs` response falls through to SearXNG/DuckDuckGo for that turn exactly like an outright failure would, so a single bad backend pick costs at most one tier's worth of quality for that one search, never a failed tool call.
- **[Risk]** Codex's `--sandbox read-only` might also block Codex's own first-party web search alongside file writes — unverified, Codex isn't installed to check directly. → **Mitigation**: documented as an open risk; verify once a machine with Codex is available. Doesn't block this change since Codex's allow-list granularity is already marked experimental.
- **[Risk]** No live per-invocation confirmation exists for Claude Code/Codex's own native tools — `confirm` degrades to `deny`, which is a real capability gap relative to what Aemeath's own Tool Registry offers. → **Mitigation**: accepted for this change; the static allow-list is still strictly safer than the alternative of guessing that `--permission-mode manual` works headless without verification.
- **[Risk]** `OpenAiCompatible`/`Anthropic` profiles get no tool-calling in this change — a user whose `default_profile` is one of those gets no agent-loop benefit at all yet. → **Mitigation**: accepted, explicit fast-follow; narrowing to one provider first was a deliberate choice to prove the loop end-to-end before committing to three separate streaming-tool-call parsers.
- **[Risk]** `cli_locator`'s login-shell fallback (Unix, step 3) spawns `$SHELL -ilc`, which runs the user's real interactive rc files — arbitrary code that could be slow (a network call in `.zshrc`) or, in a pathological config, have side effects. → **Mitigation**: bounded by a 5s timeout (falls through to "not found" rather than hanging a chat turn), the result is memoized so this only happens once per binary per process lifetime, and it's a strict subset of what already runs every time the user opens a real terminal on their own machine — nothing here executes with elevated trust.
- **[Risk]** `cli_locator`'s Windows registry read doesn't expand `REG_EXPAND_SZ` values (e.g. `%SystemRoot%`-style references in the machine-wide `PATH`), so an entry depending on env-var expansion is silently skipped. → **Mitigation**: accepted — the only consequence is missing a system-installed (not third-party CLI) location, and full expansion wasn't judged worth the added complexity for that narrow case.

## Migration Plan

Pure additive fields with safe defaults — no data migration needed. `AiSettings.task_router_mode` defaults to `Single` (identical behavior to today) and `AiSettings.project_root` defaults to `None` (file/command tools route every request through the confirmation popup until the user configures one, per the Decisions above — not a hard failure, just more friction until configured). No re-entry or re-disclosure of any existing setting. Rollback: an installation that never touches `task_router_mode`/`project_root`/the new tool settings sees no behavior change beyond the (inert until used) new AI-tab controls.
