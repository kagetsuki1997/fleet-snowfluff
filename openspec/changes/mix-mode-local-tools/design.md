## Context

`run_generation_mix_local` (`chat_commands.rs`) today drives a plain `provider.chat()` stream and buffers its first bytes through `detect_escalation` (`task_router.rs`), a character-by-character prefix match against the literal `<<ESCALATE>>` marker. `calls is_empty()` is structurally guaranteed on that path — `.chat()` is the non-tool-aware endpoint, so no `ToolCallStreamItem::ToolCall` can ever appear. This design gives the same local attempt access to `AemeathAgentRuntime`'s native tools, which requires `provider.chat_with_tools()` instead, and that reopens exactly the problem `agent-core-and-task-router`'s own design.md flagged and deferred: a tool call produces no text bytes for `detect_escalation` to look at, and `AemeathAgentRuntime::run()` has no mechanism to abort mid-stream the way today's code can `drop(stream)` on a detected `<<ESCALATE>>`.

See `proposal.md` for the motivating case (reading a local file is wastefully escalated today) and for the exact spec changes.

## Goals / Non-Goals

**Goals:**
- Let the local attempt use read-only, side-effect-free tools (`read_file`, `list_directory`, `web_search`, `get_system_context`) without reopening the ability to escalate after anything has been shown to the user.
- Reuse `AemeathAgentRuntime::run()` unmodified for every iteration after the first.
- Keep the confirmation popup (`tool_confirmation.rs`) entirely out of this path.

**Non-Goals:**
- `run_command` and `delegate_task` are never offered to this path, in any state. Not revisited here — if a future change wants them, it needs its own design pass (destructive/high-blast-radius tools interacting with a silent pre-commitment phase is a different risk profile than read-only tools).
- A smaller `max_iterations` cap for this path specifically. Uses the same cap as any other `ToolCapable` turn; a slow local loop is an accepted cost of giving the local model tools at all, not something this change tries to bound further.
- A general cancellation/abort hook on `AemeathAgentRuntime::run()`. Considered and rejected for this change — see Decision below.
- Rewriting `ESCALATE` categories unrelated to filesystem/web access (shell execution, file writes, multi-step/iterative work, browser automation, long-running tasks) — none of those map to a tool this change adds.

## Decisions

**The commitment point is "first text divergence or first tool call while text is still undecided," not every tool call.** Once text has diverged from `<<ESCALATE>>` (today's existing `Simple` outcome) *or* a tool call has been requested before text resolved either way, the whole turn is irreversibly local — there is no `Retract`/`Undo` variant on `ChatEvent` (confirmed by reading `chat_commands.rs`; it has exactly `Chunk`/`Done`/`Error`) and nothing in this codebase ever un-shows streamed text. A later `Confirm`-tier attempt in the same turn, after commitment, is therefore just a normal denial fed back to the model as a tool-result — never a popup, never a second escalation. _Alternative considered_: buffer the entire first iteration (text and tool-call classification together) before ever flushing anything, so a late-discovered denial in iteration 1 could still cleanly discard the whole thing. Rejected as unnecessary complexity for an edge case that's rare in practice (a local model reaching for a tool tends to do so with little or no preceding narration), given the chosen tools are all read-only — a wasted `read_file` call before a denial is harmless, not a correctness problem.

**`AemeathAgentRuntime::run()` is not used for iteration 1; it's hand-rolled against `provider.chat_with_tools()` directly in `chat_commands.rs`, then `run()` takes over from iteration 2.** `run()`'s inner per-iteration loop (`agent_runtime.rs:371-380`) calls `on_text_delta` live, inside the same loop that's still collecting that iteration's tool calls, and offers no way for the caller to signal "stop, drop the stream" from inside that callback. Today's escalation mechanism depends on exactly that ability (`drop(stream); drop(local_provider);` on a detected marker). _Alternatives considered_: (a) add a `ControlFlow`/`bool` return to `on_text_delta` so any caller can abort `run()` mid-iteration — rejected because it changes a signature every other `ToolCapable` caller depends on, for a capability only this one caller needs; (b) do everything inside `run()` via a custom `PermissionDecider` with interior-mutable "have we committed yet" state — rejected because the abort problem is about stream-reading, not permission decisions, and a decider can't make `run()` stop reading a stream it doesn't control. Hand-rolling iteration 1 duplicates a bounded amount of logic (classification, and sequential — not `run()`'s bounded-concurrent — execution of any `Auto`-tier calls, since a classification-style first action realistically has 0-1 tool calls, not enough to justify duplicating the `buffer_unordered` machinery too), isolated entirely to this one new code path; `agent_runtime.rs` is untouched.

**The registry is built conditionally on whether a project folder is configured.** `read_file`/`list_directory` are only ever `Auto`-tier inside a configured project folder — with none configured, every path asks for confirmation (`AI_FEATURES.md`), which under the commitment rule above would mean every attempt at either tool is either an immediate escalate (if it's the first action) or a silent denial (if not) — never useful. With no project folder configured, the registry is just `web_search` + `get_system_context` (always `Auto`, regardless of path); with one configured, all four.

**Once committed, a failure is shown as an error, not silently retried on cloud.** This isn't a new rule — it's the same distinction the existing code already makes: an infra failure *before* anything is shown falls back silently (`run_generation_mix_local`'s existing `mark_errored` + fallback branches), while a failure *after* `Simple` is decided and handed to `stream_to_completion` already surfaces as a visible error today. This change extends that same existing line to cover a failure during the tool-using continuation, rather than introducing a new policy.

**`task-router-rules.md` tells the model it may have some tools without hardcoding which ones, or teaching it the permission-tier logic.** The model's actual tool list (sent by the provider's own tool-calling mechanism) is the source of truth for what's available in a given configuration — the rules text just says to use a file-reading or web-search tool directly when offered, instead of guessing or reflexively escalating, and that anything beyond what it's been given escalates automatically. This keeps the prompt-engineering burden low: the model doesn't need to reason about project folders or confirmation tiers, since the permission layer enforces that boundary regardless of what the model attempts.

## Risks / Trade-offs

- **Every mix-local request now carries tool definitions, even for purely conversational messages.** The registry always has at least `web_search`/`get_system_context` (never empty), and iteration 1 always calls `chat_with_tools()` regardless of message content — so "hi, how are you" now costs extra prompt tokens on every single local message, not just tool-needing ones, and a model's response style can shift subtly just from tool definitions being present in context even when none is called. → Not mitigated here. Ollama's `chat_with_tools` already keeps `think: false` matching plain chat (an existing, separately-documented fix for a different problem), but the token-cost and style-shift risk is new to this change specifically and worth watching empirically; if it proves costly, skipping tools for obviously-conversational messages would reintroduce a classification problem this change deliberately avoids solving twice.
- **A small local model may hallucinate file contents instead of calling `read_file`, or misjudge a one-tool-call task as needing escalation.** → Not solved by this design; a model-capability reliability gap, not a code/permission problem. Worth empirically observing after shipping before investing further here.
- **A local model that reaches for `run_command`-shaped help (not offered) may repeat the attempt, get denied, and still try to muddle through with a worse answer than cloud would have given**, since once committed it can no longer hand off. → Accepted, matching the "once committed, no takebacks" rule everywhere else in this design; `task-router-rules.md`'s existing shell-execution `ESCALATE` category is unchanged, so a model that's actually following the rules should still escalate *before* attempting this, as the first action, not after.
- **Duplicated classification/execution logic between the hand-rolled iteration 1 and `run()`'s own internals could drift out of sync over time** (e.g. if `required_permission`'s tiering logic changes shape later). → Scoped small deliberately (sequential-only execution, no concurrency to replicate); flagged here so a future reader of `agent_runtime.rs` knows this one other call site exists.

## Migration Plan

No persisted data changes. `ExecutionRecorder` already accepts a `trace: Vec<ToolInvocation>` on `mark_completed`/`mark_errored` (used today with an empty `Vec` for this path) — this change populates it with real entries, concatenating the hand-rolled iteration 1's own trace with whatever `run()` returns for later iterations, still tagged `ExecutionPath::MixLocal`. No new `ExecutionPath` variant. Rollout is a single behavior change with no feature flag — mix mode is opt-in at the task-router-mode setting already, so only users who've turned it on and enabled Ollama are affected.
