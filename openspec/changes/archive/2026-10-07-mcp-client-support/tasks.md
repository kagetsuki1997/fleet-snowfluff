## 2. HTTP transport and OAuth

- [x] 2.1 Add an HTTP/SSE transport implementing the same JSON-RPC methods as 1.1 over HTTP, including sending `Authorization: Bearer <token>` once a token exists. Verify with a test against a mock HTTP server.
- [x] 2.2 Implement OAuth discovery: on a `401` response, parse the `WWW-Authenticate` header's resource-metadata URL, fetch `/.well-known/oauth-protected-resource` to find the authorization server, fetch `/.well-known/oauth-authorization-server` for its endpoints. Verify with a test against mocked HTTP responses for each step.
- [x] 2.3 Implement Dynamic Client Registration (RFC 7591) against the discovered authorization server, falling back to a clear, specific error (naming the server) if the authorization server doesn't support it — not a silent dead end. Verify with tests for both the success and unsupported-fallback paths.
- [x] 2.4 Implement the PKCE authorization-code flow: generate verifier/challenge, build the authorization URL, start a short-lived on-demand local redirect listener to catch the callback, exchange the code for a token (no client secret). The literal browser-launch call (`tauri_plugin_shell::ShellExt::open`) is _not_ here — `fleet-snowfluff-ai` has no `tauri` dependency, so this module produces the URL and `RedirectListener`; Group 4's `McpConnector` (`AppHandle`-backed) is what actually opens it, same boundary as design.md's own Decision on `connect_mcp_server`. The manual "paste the code" fallback needs no separate function: `exchange_code_for_token` takes any `code` string, whether it came from `RedirectListener::wait_for_code` or was typed in by the user. Verified by reading the listener's own lifecycle (starts only when needed, exits on success or timeout) and with tests exercising PKCE generation, the authorization URL, the redirect listener, and the code-exchange step against a mocked token endpoint.
- [x] 2.5 Store the resulting access/refresh token in `secrets_store`, keyed by server id. Verify with a test round-tripping a token through storage and retrieval.

## 4. `connect_mcp_server`, persistence, and removal

- [x] 4.0 **Resolved — the user chose mirroring `PermissionDecider`'s own shape, per design.md's own Decision.** A new trait `McpConnector` (`async fn connect(&self, request: McpConnectRequest) -> McpConnectOutcome`), defined abstractly in `fleet-snowfluff-ai`, implemented with a real `AppHandle` in the app crate, passed into `run()` as a new parameter the same way `permission: &dyn PermissionDecider` already is. `connect()` must itself resolve the confirm/connect/OAuth-pending three-way branch (see design.md) rather than ever blocking on OAuth completion.
- [x] 4.1 Add the `McpConnector` trait (`fleet-snowfluff-ai`) plus `McpConnectRequest`/`McpConnectOutcome` types, add `mcp_connector: &dyn McpConnector` as a new parameter to `AemeathAgentRuntime::run()`, and add a reserved name constant and a stub `Tool` impl for `connect_mcp_server` (mirroring `DelegateTool`'s shape: exists for `definitions()` discovery, `execute()` unreachable in correct operation), plus the special-cased dispatch for it _inside_ `run()`'s own per-iteration loop (`CallPlan`-style, same as `delegate_task`'s own dispatch point), calling `mcp_connector.connect(...)` in place the same way `permission.decide(...)` already gets awaited for other `Confirm`-tier calls. Update the two call sites that never actually need it (the recursive `delegate_task` call inside `run()`, and `mix-mode-local-tools`'s own continuation call) to pass a trivial, never-reached implementation mirroring `AlwaysDenyConfirm`'s own shape — safe because `connect_mcp_server` is excluded from both of those paths' registries (4.6). Verify with a test confirming the dispatch is reached for the reserved name via the same per-iteration classification pass `delegate_task` already goes through, and that the trivial implementations are never invoked from either of the two call sites that pass them.
- [x] 4.2 Wire the confirmation step: resolve the model's requested server (command/args or URL, taken as given, no allowlist match attempted) into the same `tool_confirmation.rs` popup flow already used for other `Confirm`-tier calls, showing the exact resolved command or URL. (`PopupMcpConnector`, plus `attempt_connection`/`start_oauth_flow`/`finish_oauth` — the latter never awaited by the chat turn, satisfying the "does not block the rest of the conversation" scenario.) The confirm/connect control flow itself is `AppHandle`-dependent and, like `PopupPermissionDecider::decide` elsewhere in this same file, is not unit-tested — this codebase has no `tauri::test` mocking anywhere; verified by reading the code, with its pure helpers (`summarize_connect_request`, `display_name_for`, `generate_server_id`) unit-tested directly.
- [x] 4.3 Add an `mcp_servers` config sibling to `AiSettings`, persisted the same way (`ai_config_store`-style), holding each server's connection details, status (`ready`/`pending`), and cached discovered tools list.
