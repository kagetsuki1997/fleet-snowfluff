## Context

See `proposal.md` for motivation and scope boundary. The relevant current state, confirmed against the code during `/opsx:explore stage 5` + `/grill-me`:

- `AgentRuntime::run`'s loop (`agent_runtime.rs`) collects every tool call the model requests in one turn into `calls: Vec<PendingToolCall>`, then executes them one at a time: `Auto`-tier calls run immediately in request order; `Confirm`-tier calls are batched into a single `permission.decide(&batch)` call, then — once approved — also executed one at a time, in the same loop iteration.
- `Tool::execute(&self, args: Value, ctx: &ToolContext) -> Result<ToolResult, ToolError>` only receives `ctx` (`project_root` + `conversation_id`). It has no access to `provider`, `registry`, or `permission` — those exist only as `run()`'s own local parameters.
- `ToolConfirmationState.pending: Mutex<Option<PendingBatch>>` is a single slot. `confirm_via_popup` overwrites it unconditionally; a second call while the first is still awaiting its own `oneshot::Receiver` silently drops the first batch's responder, which resolves to `Err` → `.unwrap_or_default()` → every call in that batch is treated as denied, with no error surfaced anywhere.
- `DefaultTaskRouter::route()` never reads `context.task` at all — it resolves purely on `context.mode`/`default_profile`/`local_profile`. `TaskRequirements`'s capability flags (`needs_web`, `needs_shell`, etc.) exist as a struct shape but are never inspected by the actual router, for anyone, today.
- Tool failures already propagate uniformly: `execute()`'s error becomes the tool's own `ToolResult`/trace entry, pushed back to the model, which decides what to do next. The loop itself never aborts on a tool failure.
- A child's own narration must never reach `partial_text`/`ChatEvent::Chunk` — those are driven by whichever `on_text_delta` closure is passed into `run()`, and the parent's own copy is what's wired to the visible chat window.

## Goals / Non-Goals

**Goals:**

- A model can delegate a described sub-task to its own independent agent loop and get back a result, usable from any tool-calling-capable profile.
- Delegation composes with every existing safety mechanism (permission tiers, confirmation, cancellation) without weakening any of them.
- Fix the `ToolConfirmationState` collision this change's own concurrency is the first thing to actually exercise.

**Non-Goals** (all deferred, each because nothing yet consumes it — same reasoning `execution-log-and-context` used for `ContextManager`/`ExecutionResult`):

- A persisted child `Execution` record, `parent_execution_id`, `ExecutionKind` — §6.13's full execution-tree model. Depth is capped at 1, so there is no tree to visualize yet, only a single generation of siblings.
- Context projection (§10.1's `SubAgentContextSpec`) — moved to Stage 7 in `docs/fleet-snowfluff-feature-planning.md` (already applied). Projection only has real value once there's an actual Context Engine with facts/decisions to project from.
- Runtime diversity per role/task (§6.13.4's "research child → web-capable runtime, coding child → Claude Code") — there is no capability-aware routing today, for anyone, parent or child; building one just for delegation would be new routing logic the rest of the app doesn't have either.
- Budget/cost tracking (§6.13.7) — no token/cost ledger exists anywhere today; building a concurrency-safe one is real new infrastructure, not a small guardrail.
- Any live "sub-agent status" UI (§6.13.10's "🔎 Researching / 💻 Reviewing") — no tool call of any kind is visible to the UI while in progress today; building this for delegation alone would be new, general UI machinery, not a delegation-specific addition.
- A `role` parameter — its only proposed use was cosmetic system-prompt framing with no structural effect; cut as speculative until there's evidence it changes outcomes.

## Decisions

**1. Delegation is special-cased inside `AemeathAgentRuntime::run()`'s own loop, not a generic `impl Tool`.** `Tool::execute()`'s signature cannot reach `provider`/`registry`/`permission` — recursing into a child `run()` call needs all three. Extending `ToolContext` to carry them would burden every other tool's context with fields only one tool needs, and would force an ownership change (today's `provider`/`permission` are passed as plain `&dyn` at the call site, not `Arc`-shared) that ripples outward from this one tool. Instead, `run()` recognizes a reserved tool name directly in its own dispatch — alongside the existing `Auto`/`Confirm`/`Deny` branches, which already have `provider`/`registry`/`permission` as local variables, no new plumbing required. The tool's `ToolDefinition` (schema) is still registered normally in `ToolRegistry` so `registry.definitions()`/model discovery work unchanged; only its _execution_ bypasses `Tool::execute()`. This mirrors Claude Code's own `Task` tool: the model sees an ordinary tool, calling convention and all; the harness implements it specially. Alternative considered: extend `ToolContext` with `Arc<dyn ToolCallingProvider>`/`Arc<dyn PermissionDecider>`/a registry handle — rejected for the reasons above.

**2. Depth capped at exactly 1, structurally, not by a runtime-checked counter.** A child's own `ToolRegistry` is built by filtering the parent's registry to exclude the delegation tool's name before recursing. There is no depth field anywhere, nothing to thread through `ToolContext`, nothing to get wrong at call time — a child simply never has the capability to delegate further, the same way any other omitted tool is unavailable to it. Matches Claude Code's own choice (a spawned subagent cannot itself spawn another).

**3. `delegate_task`'s schema is `{task: string}`; its own permission tier is `Auto`.** No `role` parameter (Non-Goals). `Auto`, not `Confirm`, because the real risk surface is already fully covered one level down — whatever the child actually does still goes through the exact same per-call permission check its parent's equivalent call would. Gating the decision to delegate at all would add a confirmation for something as low-stakes as splitting a summary into two parts, with no matching safety gain.

**4. No persisted child `Execution`; the result folds into the parent's own existing trace.** `delegate_task`'s outcome becomes an ordinary `ToolInvocation { name: "delegate_task", outcome: ToolOutcome::Executed { ok } }` in the parent's own `AgentOutcome.trace` — exactly like any other tool call. This means the tool-activity-carryover note `execution-log-and-context` already built (`ContextManager::build_context` reading the immediately preceding `Execution`'s trace) picks up delegation automatically, with zero new code: a turn after a delegation-using turn already gets told "delegate_task: executed successfully," the same as it would for `run_command`.

**5. A delegated child gets a plain, task-focused system prompt — never Aemeath's persona framing — and its own `on_text_delta` is a discarding no-op closure.** The child's output is read by the _parent model_, not the end user; persona framing (speech style, boundaries, in-character warmth) is tuned for the latter and would make the child's report actively harder for the parent to use, not just unnecessary. A new, small function alongside `prompt::build_system_prompt` builds this — something like _"You are completing a focused sub-task delegated by another process. Complete the task below and report your findings concisely — your response is read by another AI, not the end user."_ Passing a no-op `on_text_delta` (rather than the parent's real one) is the actual mechanism that keeps a delegated sub-task invisible while it runs (Non-Goals' "no live status") — without it, the child's narration would stream straight into the visible chat transcript, interleaved with the parent's own.

**6. A delegated child reuses `DefaultTaskRouter::route()` completely unmodified — same profile as its parent, no runtime diversity.** Since the router never reads task content for anyone today, building per-child routing would be new capability-aware logic the rest of the app doesn't have either. A child still gets real value from delegation without runtime diversity: scope isolation (a focused task, not polluting the parent's own message history) and genuine wall-clock speedup from concurrent fan-out against the same provider.

**7. Tool-call execution within one turn becomes concurrent, bounded (not delegate-specific).** Today's loop runs every `Auto`-tier call sequentially, one `.await` at a time. This changes generally — using `futures_util::stream::iter(...).buffer_unordered(N)` (a fixed default, `N = 3`) rather than an unbounded `join_all` — because unlike every other existing native tool, a delegated sub-task's own blast radius (a full nested agent loop, potentially a CLI subprocess, potentially several provider round-trips) is categorically larger than `read_file`'s. `buffer_unordered` throttles total in-flight concurrency without rejecting or dropping any call; excess calls simply start as earlier ones finish. **Correctness requirement this introduces**: `message.rs`'s own doc comment notes Ollama pairs tool results with calls _by order_, ignoring `tool_call_id` — OpenAI/Anthropic use the id. Running calls concurrently means results can _complete_ out of request order; they must still be written back to `messages` in the _original_ request order (collect into a slot array indexed by original position, then push 0..n), or Ollama will silently pair the wrong result with the wrong call. Alternative considered: special-case concurrency to only `delegate_task` calls, leaving every other tool sequential — rejected per explore-session discussion: this is the more idiomatic pattern (how Claude Code's own harness and LangGraph's `ToolNode` already work — parallelize independent calls generally, not one tool specially), and it benefits every multi-tool-call turn, not only delegation.

**8. `ToolConfirmationState.pending` becomes a queue, not a single `Option` slot.** This is a real, pre-existing bug this change's own concurrency is the first thing to actually exercise — not introduced by it. Today it's safe only because exactly one `AemeathAgentRuntime::run()` call is ever in flight (the app's single-generation invariant); concurrent children (Decision 7) are the first case where two `confirm_via_popup` calls can genuinely overlap. Each call enqueues its own batch and awaits its own turn; the UI shows one batch at a time. Not a compromise — a person can only actually attend to one confirmation at a time regardless of how many tool calls ran concurrently, so this matches the one real bottleneck (human attention) rather than pretending it isn't there. Alternatives considered: merge concurrently-arriving batches into one combined popup (more "correct"-feeling, meaningfully more complex — a merge window, starvation risk, for a marginal UX difference); deny whichever call arrives second (cheapest, but a tool call could fail purely on timing, through no fault of the model or the user).

## Risks / Trade-offs

- [No context projection means a delegated sub-task starts with zero parent-conversation knowledge] → accepted; the delegating model already holds the full parent context in its own window and can (and must) write whatever facts matter directly into the task string. This is implicit, not structural, context-passing — a real limitation for tasks that need extensive prior context, acceptable for the kind of bounded, self-contained sub-tasks this change targets.
- [No budget/cost tracking under concurrency] → a model could request several concurrent delegations, each spinning up its own provider calls, with nothing accounting for aggregate spend. Partially bounded by the fixed concurrency cap (Decision 7), not eliminated. Accepted as a known gap; revisit if real usage shows it matters.
- [Concurrent children load the user's own machine — multiple CLI subprocesses or API requests at once] → bounded by the same concurrency cap; this is a desktop app sharing the user's machine, not a server with elastic capacity, so the cap is deliberately conservative (3).
- [Cancellation under concurrency] → not actually a new risk: concurrent children are futures nested inside the same outer task via `buffer_unordered` (cooperative polling within one task, not separately spawned tasks), so the existing single `JoinHandle::abort()` on Stop still drops everything nested inside it, parent and every in-flight child, uniformly.
- [Ollama's positional tool-result pairing under concurrent completion] → addressed directly in Decision 7: results are written back in original request order regardless of completion order, not dependent on provider-specific id pairing.

## Migration Plan

Purely additive. `Tool`/`ToolContext`'s existing shape is unchanged; every existing native tool, every existing call site of `AgentRuntime::run`, and every existing test double is unaffected except by the (behavior-preserving for single-call turns) switch from sequential to bounded-concurrent dispatch. No data format changes, no existing persisted file touched. Rollback is reverting the change; there is nothing to migrate back.
