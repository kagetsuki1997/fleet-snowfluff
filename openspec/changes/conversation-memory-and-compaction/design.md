## Context

See `proposal.md` for motivation and `docs/agent-foundation-memory-architecture.md` for the full exploration, including the comparison with tact, Ogham, and loopctl. This document records how the change fits the code that exists.

Facts about the current code that shape the approach:

- `AemeathContextManager::build_context(session_path, persona, language, user_message)` reads the session log, caps it with `cap_history(.., CONTEXT_WINDOW_TURNS)` (the constant is 20 **messages**, i.e. about 10 exchanges), and assembles `[system, few-shot, history, user]` through `prompt::assemble_messages`. It already prepends a tool-activity note to the user message. `record_execution(session_path, reply)` appends the assistant entry.
- Sessions are JSONL (`chat_log_store`), entries are `{role: User|Assistant|Error, content, timestamp}`, and the TypeScript UI mirrors that `LogRole`. Tool results are never persisted in history.
- In `send_chat_message` the history is read, the context is built, and the user entry is appended afterwards; generation then runs in a spawned task (`run_generation_with_tools` and the mix-mode variant). Mixed mode builds **two** message sets, a persona-only one for the default profile and one with routing guidance for the local attempt.
- A delegated child's tools are the parent registry minus `delegate_task` (verified in the runtime's tests). Anything else the parent has, the child inherits.
- Tools are `Tool` trait objects; native tools that need a service hold it themselves (e.g. `WebSearchTool` holds its transport). `native_tool_list()` builds the top-level set, `mix_local_tool_registry` the read-only local set.
- No database dependency exists yet; all stores are JSON or JSONL.
- Ollama silently drops a model's call to a tool absent from the request, which is why lazily hidden tools had to become stubs. Memory tools must therefore be eager.

## Goals / Non-Goals

**Goals:**

- Nothing the user said is lost to the model without a trace: dropped turns become a summary, and durable facts become memories.
- Every moving part is fail-safe: a broken summary, store, or background model never blocks or loses a chat message.
- Everything stored about the user is visible and erasable by the user.
- Storage is replaceable behind a trait, so embeddings can be added later without touching the runtime.

**Non-Goals:**

- Embeddings, `semantic-memory`, RAG, a project-facts namespace, mood or affection, sub-agent context projection (see proposal).
- Cross-language recall beyond keywords the assistant attaches at write time.
- Rewriting history or the session log format.

## Decisions

**The summary lives in a sidecar file, not in the session log.** A file next to the session records `{covered_through, text, updated_at}`. Adding a `Summary` role to `LogEntry` was rejected: it would change the JSONL schema, `entries_to_context`, and the TypeScript `LogRole`, for no benefit, and it would put model-written text inside the record the user reads. With a sidecar, a missing or corrupt file simply means no summary, which is the fail-safe state, and the transcript stays exactly as written.

**The summary is a pure, restartable function of the transcript.** It always covers the first `covered_through` messages of the context-visible history, where "context-visible" means the log entries `entries_to_context` keeps (error entries are skipped, so the index is over that filtered list, and the sidecar also stores the timestamp of the last covered entry as a guard against drift). A compaction takes the not-yet-covered slice that has fallen outside the history budget, asks the model to merge it into the existing summary, and only then advances `covered_through`. If it fails or the app quits mid-way, nothing is lost: the next trigger covers the same slice. There is no gap while a summary is pending, because uncovered turns that fell outside the budget keep being sent, up to a hard upper limit (see the history decision below).

**Compaction is batched and runs in the background, never before or during a reply.** `record_execution` is the hook, but it only notes that more uncovered content exists. A compaction starts when the uncovered slice reaches a size threshold, the session has been quiet for a short period, and no reply is being generated for it; otherwise the idle and close triggers cover it. This keeps summarization to a few calls per long conversation instead of one per reply, which matters for CLI quota and for a local model that would otherwise be busy exactly when the user sends the next message. One task per session is in flight at a time; extra triggers coalesce, and repeated failures back off per session so a down Ollama is not hammered. The idle and close triggers use a small scheduler that tracks last activity per session and the chat window's close event.

**The history sent with each request is bounded by a token budget, not a message count.** `cap_history(.., CONTEXT_WINDOW_TURNS)` is replaced by a selection that takes the newest messages that fit the budget, plus any uncovered older messages up to a hard upper limit, under a hard cap on message count as a backstop against floods of tiny messages. The budget is the smaller of a fixed constant and a share of the loaded model's window. The constant keeps behavior the same across machines in the normal case (the other Stage 1 guardrails are constants too, not user-configurable). The share keeps history from crowding out everything else on a small window (Ollama's default window is only 4096 tokens below roughly 24 GB of VRAM); the persona itself is protected by the fit check in the next decision, not by this share. A message count alone was rejected: it drops the same number of messages whether they were one word or a pasted page, so it neither bounds cost nor uses the context that is available, and it would trigger a summary on nearly every reply. A budget derived only from the window was rejected: the same chat would be treated differently on different machines. The estimator is the calibrated per-class rule in Spike results, deliberately conservative.

**The persona is pinned by a fit check before every request, not by luck.** Measured on this project's Ollama (qwen3:14b), when history overflows but the system prompt fits, Ollama's chat layer keeps the system message and drops older history, so the persona survived windows of 512 and 256 tokens. The failure is different: when the system prompt plus the latest message do not fit, the server truncates the raw prompt (it logged `truncating input prompt ... keep=4`) and the persona is destroyed; the reply fell back to a generic greeting. Ollama's template also renders tool definitions into the system turn, so a long tool list can push a small window into that state, and the fixed 4096-token reply allowance counts against the window too. So before each request the runtime computes the fixed cost (persona and routing rules, few-shot examples, tool definitions including stubs, the current message, a reply allowance, and a safety margin) against the window. If it fits, the history budget is the smallest of the constant, 40% of the window, and what is left. If it does not fit, it sheds in a fixed order: older history, keyword-matched memories, the summary, the digest, few-shot examples, stub tool listings, then reduces the reply allowance toward a floor. If the persona, the current message, and the floor still do not fit, the request is not sent and the user is told the context window is too small. Raising `num_ctx` for the request was rejected: changing it makes Ollama reload the model, and it would override the user's own, larger setting. For CLI-backed profiles the persona already travels outside the conversation (Claude Code through `--system-prompt`, Codex through an instructions file), so their own compaction cannot summarize it; a test asserts it never appears in a turn. Because the window is only known for a loaded Ollama model, the first request for a model loads it with an empty generate call and reads `/api/ps`; the result is cached per model. After each response, a tripwire compares the server's reported prompt size with the estimate: reported below half the estimate is treated as silent truncation (the spike showed `prompt_eval_count` includes cached tokens and reports the truncated size, so this is reliable for severe truncation, though a mild trim is not detectable this way).

**Values after the spike.** Confirmed by measurement where it was possible, and adjusted where measurement showed a problem (see Spike results); the ranking formula is a reasoned choice, not a measured one.

| Setting | Value |
|---|---|
| History budget | min(3,000 tokens, 40% of loaded window) |
| Hard message cap / uncovered allowance | 60 messages / up to 1,500 further tokens |
| Batch threshold / quiet period / idle timeout | 1,200 uncovered tokens / 20 s / 10 min |
| Digest / keyword block | 400 tokens (about 15-20 facts) / at most 5 hits within 400 tokens |
| Tool-output bound | min(6,000 estimated tokens, 25% of window); the model gets the beginning up to the bound |
| Spill retention | 200 files or 7 days; at most 50 parts of 18 KiB per result |
| Summary cap | 800 tokens |
| Safety net | 80% of the loaded window |
| Reply allowance / floor | min(4,096, 25% of window) / 512 tokens |
| Fit-check safety margin | 10% of the window |
| Keyword score floor | −2.2 (re-check as the memory count grows) |
| Digest ranking | pinned first; then importance (1 to 3) plus 2 × exp(−age in days / 30), newer first on ties. Chosen without real usage data; revisit after real use |

The tool-output bound is in estimated tokens, not characters: for CJK text one character is about one token, so a character limit that is comfortable for English could fill an entire window.

**The background model is picked by a single function.** The local profile if enabled, else the default profile. The provider is built fresh from the existing profile factory with a default `CliContext` (no `resume_session_id`), and its session id is discarded, so a CLI profile's chat session is never read or changed.

**The token safety net is a last resort inside `run()`, and the window size has one source per provider.** Before each provider call the runtime estimates request size with the calibrated estimator (see Spike results; tact's simpler rule of ASCII at four characters per token underestimated structured text by up to 4x when measured here). Past about 80% of the model's window it stubs the oldest tool results, keeping the latest few, with a pointer to the spilled output. tact ships this "micro-compaction" off by default because it breaks prefix caching, so here it fires only under real pressure. The window comes from: Ollama's `/api/ps` `context_length` for the loaded model (verified on this machine: 32768 for qwen3:14b, whereas `/api/show` only reports the trained maximum, 40960, which would overestimate); a small built-in table of known models for OpenAI and Anthropic API profiles, with a conservative default for unknown names so the net triggers early, not late; and nothing for CLI-backed profiles, which run their own context management and never go through this loop. Before the first request of a run the Ollama model may not be loaded yet; the request is small then, and the conservative default applies.

**Tool-output bounding is separate from compaction, and the spilled output is readable in pieces.** A single bound applies to every tool result at the point it is added to `messages`, in the runtime, so native and MCP tools are treated alike. The model receives the beginning of an oversize result up to the bound, followed by a marker; the rest is written under a dedicated directory in the app data directory. `read_file` reads at most 20 KiB of a file and has no offset, so one large spill file could never be read past what the model already has; the rest is therefore saved as numbered parts of at most 18 KiB each (up to 50 parts, with the marker saying when the very end is not saved), and the marker names the first part. `read_file` outside the project root is Confirm tier today (and always Confirm when no project root is set), so without an exception that path would trigger a confirmation every time or never be read. The tool itself carries one narrow exception: an absolute path inside the spill directory, after `..` and symlinks are resolved, is Auto. Nothing else about file permissions changes, and the spill directory is pruned by age and count.

**Memory lives behind a `MemoryService` trait in `fleet-snowfluff-ai`, backed by SQLite.** `rusqlite` with the bundled SQLite, one database file in the app data directory, WAL mode, schema version tracked with `user_version`. The driver is synchronous, so calls run through `spawn_blocking`. A failure to open or query returns an error the caller treats as "no memory this turn". `semantic-memory` was rejected for v1: its writes require an embedder with no fallback, it is research-grade, and its default vector backend needs a C++ bridge across three desktop platforms. Plain files plus an in-memory index were rejected because the background pass and a chat turn write concurrently, and we want atomic writes and a clean upgrade path.

**Keyword matching is done on text we pre-tokenize, not by SQLite's tokenizers.** Memory text is split by script. Latin runs become lower-cased words; Han, kana, and Hangul runs become overlapping character bigrams; the result is stored as a space-joined token string in an FTS5 column that SQLite indexes with its plain tokenizer, and BM25 ranks it. Queries are tokenized the same way, and a small English stopword list is applied to Latin words (the spike showed English recall collapsing without it on a hostile corpus). SQLite's trigram tokenizer was rejected because it cannot match under three characters and many Chinese words have two. A one-character query term falls back to a substring scan of the normalized text, which is cheap at this scale and avoids indexing noisy unigrams. Dictionary segmenters were rejected for their size and per-language handling.

**Traditional-to-Simplified normalization is a checked-in character table, kept because the spike showed it helps.** Recall on mixed Traditional/Simplified queries rose from 17/24 to 19/24 with it and was unchanged without mixing, so the table and task 3.4 stay (see Spike results). Matching only needs a one-to-one character mapping, not phrase-level conversion, so a generated constant table (derived from OpenCC's character data, Apache-2.0) is enough and avoids a dependency. Both index and query go through it; the stored text is untouched.

**Ranking for the digest is a simple weighted score.** Pinned first, then a blend of importance and an exponential recency decay, within a token budget. Keyword hits are ranked by BM25 with a floor below which nothing is injected. The weights and budgets are tuned in the spike, not guessed here.

**Sensitivity is enforced at the query, by audience, and covers saved entries only.** `build_context` takes an audience, local or cloud, derived from the profile that will handle the request (Ollama and Mock are local; every OpenAI or Anthropic profile, including CLI-backed ones, is cloud). The store's query excludes sensitive rows for the cloud audience, so there is no post-filter to forget. Mixed mode already builds separate message sets for the local attempt and the default profile; each gets its own audience, so an escalation to a cloud default does not carry sensitive memories. Memory tool results are filtered the same way. The guarantee is deliberately narrow: a fact the user typed into the chat is still part of the conversation text sent to a cloud profile, and the disclosure says so rather than implying otherwise.

**Memory tools are native tools holding an `Arc<dyn MemoryService>`.** `memory_search` and `memory_get` are read-only and Auto tier, and appear in the top-level, local, and child registries. `memory_remember`, `memory_forget` (Confirm tier, through the existing popup), and `compact_context` appear only in the top-level registry. Because a child inherits everything but `delegate_task`, `Tool` gains an `available_to_children` flag defaulting to true, and the write tools and the compaction tool return false; the existing child-registry derivation drops them the way it drops `delegate_task`. The tools take no scope argument. All five are registered as eager.

**`memory_remember` goes through a write policy; host-side paths cover weak models.** The policy dedupes against active memories (normalized equality, with Traditional and Simplified spellings, case, and whitespace folded; a paraphrase is stored again, since merging by keyword overlap risks fusing two distinct facts, and the user can delete duplicates in Settings) and applies `supersedes` when a correction names a prior memory. A small local model may not call the tool, and may not know the id of the memory it would be correcting, so the host has two backstops that do not depend on the model. For an explicit "remember" phrase in the user's message (a short phrase list per language), it runs a one-turn extraction after the reply. For a correction cue, it searches the existing memories for the few closest matches and puts them, with their ids, in the one-turn extraction prompt, so the model only has to pick which id the new fact replaces; if none fits it stores a new memory. Dedupe prevents a double write when the model's own tool call also fires. Both run in the background after the reply, so they are prompt but not strictly before the next message.

**Details settled while building the store.** A memory's status is only active or superseded; there is no "deleted" state, because forgetting erases the row, its index entry, and (with `secure_delete` and a WAL checkpoint) its bytes in the file. A memory the user asked for whose text matches the sensitive-topic screen is saved with `sensitive` set, so asking the assistant to remember a medication never sends it to a cloud profile; a derived memory that matches is discarded. The relevance floor scales with the number of memories (capped at 70% of what a single-keyword hit can score under BM25, and the full −2.2 from about thirty memories), because a fixed floor discards every true match in a store of three. For corrections, the closest keyword matches are padded with the best-ranked memories, since a corrected fact often shares no words with the old one ("Taichung" versus "Taipei").

**Extraction at compaction proposes, the policy disposes.** The prompt asks for a JSON list of candidates (text, kind, importance, tags in the user's language and English) and forbids the sensitive categories; a deterministic sensitive-topic screen (per-language term lists, shared with the summary path) then discards any candidate it matches. Parsing is lenient; a bad response yields no candidates. Auto-derived memories only dedupe, never supersede: contradiction detection without embeddings is unreliable, so a derived fact never overwrites one. Supersession is reserved for the user's explicit corrections.

**Settings gets its own Tauri commands, mirroring the MCP ones.** List, update, pin, mark sensitive, delete, and history, with a change event so the open list refreshes, reusing the `<details>` row pattern and the five locale files.

**The cloud disclosure gains a memory sentence, and every cloud pair is re-prompted.** The existing rule that changed disclosure text clears an earlier acknowledgement is extended from API-key pairs to all cloud pairs, subscription-backed ones included: memory brings old conversation content back into later requests, which is a materially new data flow even for a subscription account the user already trusts with messages. A cloud profile that has not acknowledged the new wording is not used for chat until it does, and the settings row shows the disclosure with a way to acknowledge it. The sentence states that saved memories and summaries may be sent, that sensitive saved memories are not, and that text typed into the conversation is not covered by that exception.

**A master switch turns memory off.** With it off there is no digest, no keyword retrieval, no memory tools, and no extraction; existing memories stay stored and untouched, and a "delete all memories" action erases them. The switch is on by default once AI is enabled, because the disclosure and the review list are the safeguards; compaction itself is not tied to it.

## Risks / Trade-offs

[Summary-of-summary drift: each compaction rewrites the previous summary and details erode] → bound the summary size, instruct the model to merge not append, keep the transcript on disk, and let the model request a focused compaction.

[The estimator or window is wrong and the persona is truncated anyway] → the safety margin and a conservative estimator make that unlikely, a hard pre-flight refusal replaces silent damage when the fixed cost alone cannot fit, and the post-response tripwire logs and surfaces truncation so the budget can be tightened.

[A small local model summarizes or extracts poorly in some languages] → extraction is advisory and reviewable; failures leave things unchanged; the spike checks all five languages before the prompts are frozen.

[Bigram matching is noisy, and recall without embeddings misses paraphrase] → the digest needs no matching; tags attached at write time bridge some synonyms and English; the model can query deeper through its tool; the store sits behind a trait so an embedder can be added.

[Sensitive-topic exclusion cannot rely on the model: in the spike, extraction leaked a medication fact in 1 of 15 runs and every summary kept it despite an explicit instruction] → a deterministic per-language keyword screen runs on every derived candidate and every summary as a second layer, at the price of occasionally dropping a harmless sentence (a dentist visit counts as health); everything is listed in Settings with a sensitive flag, and sensitive saved memories are withheld from cloud profiles (text the user typed into the chat is not covered, and the disclosure says so).

[First SQLite dependency adds a C build step and about a megabyte to the binary] → the bundled build is standard in Tauri apps; verify the three-platform release pipeline early, in the spike.

[Background calls to a CLI profile cost startup time and subscription quota] → accepted by decision; batching makes calls few (a size threshold after a quiet period, plus idle and close), coalesced, and backed off.

[A compaction races the next message, or competes with it for a busy local model] → compaction starts only after a quiet period and never while a reply is being generated, uncovered turns keep being sent meanwhile, and a missed compaction is simply redone from the transcript.

[Re-prompting every cloud user, API-key and subscription, with the updated disclosure] → intended; chat on those profiles waits for one acknowledgement, and the release notes say so.

[Host-side "remember" and correction detection misfires or misses] → a false positive only runs a one-turn extraction whose output is deduped and reviewable; a miss falls back to the model's tool and to compaction-time extraction. A wrong supersede is visible in the memory history and can be undone there.

[The token estimator is rough for CJK, so the budget could be exceeded or under-used] → it errs high, the hard limits bound the worst case, and the spike compares it with the server's reported prompt size.

[Memory text derived from web or tool content could carry injected instructions] → everything injected sits in a labeled untrusted block outside the system prompt, and memories derived from tool-heavy turns are lower importance by default.

## Migration Plan

Additive. The database and summary sidecars are created lazily on first use, so existing installs and sessions work unchanged. Existing long sessions are summarized lazily when they are next used, not scanned at startup, and the first summary of a long transcript is built from a bounded recent portion of the dropped region. Rollback is to delete `memory.db` and the summary sidecars; no existing data format changes. The updated disclosure takes effect on first launch after the update.

## Spike results

**Task 1.1: keyword matching (prototype in `scripts/spikes/memory/`, fixtures in `crates/fleet-snowfluff-ai/tests/fixtures/memory/`).** Script-aware tokenizer, character bigrams for CJK, words for Latin text, FTS5 with BM25, English stopwords, score floor −2.2, 30-memory corpus, recall@5:

| Language | lexical | Latin inside CJK | one character | English tag | inflection | paraphrase (expected miss) | false matches on negatives |
|---|---|---|---|---|---|---|---|
| en | 20/20 | - | - | - | 2/2 | 0/5 | 0/3 |
| zh-Hant | 15/16 | 3/3 | 2/2 | 3/3 | - | 0/3 | 0/3 |
| zh-Hans | 15/16 | 3/3 | 2/2 | 3/3 | - | 0/3 | 0/3 |
| ja | 13/13 | 3/3 | 2/2 | 3/3 | - | 1/6 | 0/3 |
| ko | 15/15 | 3/3 | 1/1 | 3/3 | - | 1/5 | 1/3 |

What it means:

- The spec's keyword scenarios pass: two-character Chinese words, Latin words inside CJK text, one-character terms (through the substring fallback), and English tags reaching CJK memories.
- Paraphrase queries are almost all missed, as expected without embeddings. This is the cost of the decision, now measured. Four queries first labeled "lexical" turned out on review to share no content word with their memory ("what my job is" against "Works as a software engineer") and were relabeled paraphrase.
- One genuine weakness: 「這個太辣了我吃不了」 does not find 「不敢吃辣」, because the character 辣 sits in different bigrams. Bigram matching misses when the shared word is a single character inside different phrases.
- **Normalization stays.** On cross-script queries (Traditional queries against Simplified memories and the reverse) recall rises from 17/24 to 19/24. Same-language recall is unchanged. Most remaining cross-script misses are vocabulary differences between regions (腳踏車 versus 自行車), which no character mapping fixes.
- **English needs a small stopword list.** On a deliberately hostile corpus (1,000 distractors, each spliced from three real memories), English recall fell to 11/22 and recovered to 17/22 with stopwords; Chinese held at 22/24, Japanese at 17/21, Korean at 20/22 without any list. That corpus is far harsher than real use; the list is cheap insurance.
- **The score floor** of −2.2 separated every true top hit (weakest −2.52) from the strongest false match (−1.92) on these fixtures. BM25 magnitude depends on corpus size, so −2.2 is a starting value to re-check as real memory counts grow.
- Korean had one negative query still matching (a common word in the query), the only imperfect separation.
- The planned run on real chats was **not done**: no labeled real conversations exist, and unlabeled chats cannot give recall. The synthetic fixtures and the hostile-corpus test stand in for it; anyone can add labeled queries to the fixture files to extend the measurement.

**Task 1.2: SQLite.** A scratch binary with `rusqlite` (`bundled`) builds on macOS, runs FTS5 queries (SQLite 3.50.2), and is about 1.15 MB larger than the same binary without it (1,436,928 versus 285,824 bytes, size-optimized, stripped). Windows and Linux could not be built from this machine. They are inferred, not proven: the workspace already compiles C code on all three release targets through `aws-lc-sys` (via `rustls`, via `reqwest`), which needs a stricter toolchain than SQLite's single C file. Task 1.2a keeps an explicit CI confirmation open.

**Task 1.3: window and estimator.** Ollama's `/api/ps` reports the loaded model's runtime window (`context_length`, 32768 for qwen3:14b) while `/api/show` reports only the trained maximum (40960). The planned estimator (ASCII at four characters per token, other characters one token) was measured against the server's prompt token counts on 14 samples and **underestimated structured text badly**: JSON 0.57x, log lines 0.43x, markdown tables 0.48x, digits 0.25x, code 0.63x (prose and CJK came out 1.0 to 1.5x). Tool output, which the bound exists to protect, is exactly the structured case. Replaced by a per-class rule: letters 0.25, digits 1.0, punctuation 1.0, whitespace 0.1, non-ASCII characters 1.0, all multiplied by 1.15. Measured ratio of estimate to actual: 1.03 to 1.66 across all 14 samples, never below 1. It is calibrated against qwen3's tokenizer only; other tokenizers differ, but cloud models have large windows, so the risk there is cost, not overflow. The built-in window table for API profiles is deliberately small and conservative: model names starting with `claude-` map to 200,000 tokens; names starting with `gpt-4o`, `gpt-4.1`, `gpt-5`, `o1`, `o3`, or `o4` map to 128,000; anything else falls back to 32,768. The cloud APIs reject an over-long request with a visible error rather than trimming it silently, so a wrong entry costs an error, not the persona, and entries are cheap to add as models change.

**Task 1.5a: persona and truncation** (`scripts/spikes/memory/persona_truncation.py`). Reproduced on qwen3:14b: with the persona prompt fitting, history overflowing windows of 512 and 256 tokens left the persona intact (the reply stayed the forced one-word answer). When the persona prompt alone exceeded the window, the server truncated the raw prompt and the persona was lost. `prompt_eval_count` includes cached tokens (the cached count is a subset), so it reflects the full processed prompt, and in the truncation case it reported the truncated size (130) against a much larger real prompt. A reliable tripwire is therefore reported prompt size well below the estimate (below half), which our estimator, never under 1.0x, makes safe. An "at the limit" check is not reliable: the truncated prompt landed at 130 for a window of 256, not near it.

**Task 1.4: background prompts** (`scripts/spikes/memory/prompts_spike.py`, qwen3:14b, five languages, one chat each with durable facts, small talk, a correction, and a medication mention):

- *Extraction:* valid JSON in 15 of 15 runs and all three expected facts found in 15 of 15. The sensitive medication fact leaked in 1 of 15 runs in the first pass and 0 of 15 in the second, so the instruction alone is unreliable.
- *Correction:* the right memory id was chosen in 5 of 5 languages, with a short corrected text.
- *Summary language:* with the language stated only in an English instruction, zh-Hant, ja, and ko summaries came back in English. Passing the language explicitly ("write the notes in Traditional Chinese (繁體中文)") fixed all five.
- *Summary sensitivity:* with an explicit "leave out health and medication" rule, 5 of 5 summaries still kept it. Summaries persist and ride along on every later request, including to cloud profiles, and the user cannot review them in Settings, so the summary now gets the same deterministic screen as derived memories (a new requirement in `context-compaction`).
- The prompts as tested are in the script and are the starting point for tasks 2.9, 3.15, and 5.1.

**Task 1.5: fixed cost and the 4096-token case.** Measured on qwen3:14b with the real persona, few-shot examples, native tools, and 43 stubs (`prompt_eval_count` differences at a 32768 window): persona and one message 590 tokens, few-shot examples 115, eight native tools 925, the 43 stubs 1,687, for 3,334 before any history. At a 4096 window that leaves roughly 760 tokens before a reply is even reserved, so the shed order must engage there: with the margin and a 512-token reply floor, few-shot examples and the stubs go first, leaving the persona, the eight native tools, and about 1,600 tokens for history and memory blocks. In every configuration tried (full, native tools only, no stubs or few-shot, persona only) at both 4096 and 8192, the persona survived and the reply followed it. Adjustments made from this: the tool-output bound scales with the window (min of 6,000 estimated tokens and 25% of the window), the reply allowance is min(4,096, 25% of the window) with a 512 floor, and the keyword matches, summary, and digest take part in shedding. The history budget formula (min of 3,000 and 40% of the window) is unchanged: at 4096 it gives about 1,640, which the fit check then trims to whatever is left.

**Tasks 2.1 to 2.17 (built; findings worth keeping).**

- The pre-flight fit check lives in `fit.rs` as a pure function over the assembled message list, so it sits in front of every dispatch path without threading new structures through them. It relies on the system prompt being message 0, the few-shot count, and block tags; the memory block must use a `<digest>` and a `<matches>` section so it can be shed in two steps (task 3.8 must follow that).
- Run against the real persona and tools at a 4096-token window, the check shed the few-shot examples and the stubs, lowered the reply allowance to 1,024, and refused at 2048 and 1200. Sent to the live model, both the fitted request (1,532 prompt tokens) and the unfitted one (3,486) kept the persona on this machine's current tool set, so today the check chiefly protects reply headroom and gives a clean refusal when the persona truly cannot fit. The destruction measured earlier needed a system prompt larger than the window.
- `ToolCallStreamItem` gained a `PromptTokens` item carrying the server's own prompt count from the final stream line; the agent loop warns in the log when it is under half the estimate.
- A compaction folds what the latest request left out: when the fit check trims history, the scheduler is told the history actually kept, so trimmed turns are summarized rather than lost.

### Live check of the model-dependent paths
