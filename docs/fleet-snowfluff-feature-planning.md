# Fleet Snowfluff 功能規劃摘要

> 本文件整理自一次關於「桌面寵物新功能與 AI 整合」的討論，涵蓋功能發想、AI provider 整合架構、性格設定、情境感知等主題。目的是作為後續深入規劃（例如搭配 openspec）的輸入來源，非最終規格書。
>
> 專案背景：Fleet Snowfluff 是以 Rust 重寫的跨平台桌面寵物（原始碼庫已具備遊蕩/跟隨/好奇狀態機、拖曳語音反應、多實例、縮放/透明度、系統托盤、五種 UI 語言等功能）。目前完全沒有 AI 能力，本文件討論的是如何在既有架構上疊加 AI 互動層。

---

## 1. 新功能發想

### 1.1 互動與陪伴類

- **對話氣泡**：點擊寵物跳出輸入框，打字互動，以文字氣泡回覆。比純語音片段更有彈性，且是驗證「聊天好不好玩」的最小可行版本。
- **情境吐槽**：讀取當前作用中視窗、系統狀態（CPU/電量/時間），主動講一句應景的話。細節見第 4 節「情境感知」。
- **情緒系統**：依互動頻率/時間累積好感度或心情值，影響動畫與語音選擇。
- **多寵物互動**：專案已支援多實例，可讓兩隻寵物靠近時觸發「對話」動畫，適合用 AI 生成互動內容。

### 1.2 生產力類

- **番茄鐘/休息提醒**：主動提醒休息，建議依實際使用模式（情境感知規則）判斷，而非死板計時。
- **剪貼簿助手**：選取文字後右鍵選單加一個「問問牠」，把選取內容丟給 AI 摘要或翻譯。
- **系統通知代理**：接 calendar/待辦事項，寵物主動唸出今天行程。

### 1.3 技術類

- **語音輸入**：接麥克風 + STT，直接用講的互動（本次討論已排除語音相關細節，僅列為未來方向）。
- **外掛/腳本系統**：讓使用者自訂觸發規則（例如「偵測到某網站在背景執行就講一句話」）。

## 2. AI Provider / 本地模型整合架構

### 2.1 核心設計：Provider 抽象層

以 Rust trait 定義統一介面，讓雲端 API 與本地模型可以無縫切換：

```rust
trait AiProvider {
    async fn chat(&self, messages: Vec<Message>) -> Result<Response>;
}
```

分別實作：

- `OpenAiCompatible`：可指向 OpenAI / Anthropic API，或任何 OpenAI 相容端點
- `Ollama`：本地 HTTP server（`reqwest` 呼叫），使用者需另外安裝 Ollama + pull 模型（建議 Qwen2.5-3B、Gemma2-2B、Phi-3.5-mini 等小模型）
- `Embedded`（內嵌模型）：用 Rust 原生的 **candle**（HuggingFace 出的 ML framework）直接跑 GGUF 模型，不依賴外部程式，缺點是打包體積會明顯變大

使用者在設定裡選擇 provider + 填 API key/端點，UI 只需要一個下拉選單即可切換。

### 2.2 整體資料流

```
輸入來源（使用者輸入 / 系統情境）
        ↓
Persona + Prompt 組裝（性格設定檔 + 對話記憶）
        ↓
Provider 抽象層 ── 雲端 API / Ollama / 內嵌模型（三選一，可切換）
        ↓
回應 + 情緒標籤（AI 回覆文字 + emotion tag）
        ↓
輸出分派 ── 對話氣泡 / TTS 語音 / 動畫觸發
```

### 2.3 隱私設計原則

- 任何會讀取螢幕/視窗標題/剪貼簿的功能，預設關閉、使用者主動開啟
- UI 上清楚標示哪些資料會離開本機（雲端 API）、哪些不會（本地模型）
- 這對開源專案的信任度影響很大，建議在文件與設定介面都明確揭露

## 3. 性格（Persona）設定

### 3.1 不是用 SKILL.md 的邏輯

SKILL.md 是操作型指令（怎麼完成某類任務）。性格設定屬於 **character card / persona**，本質是塞進 system prompt 的一段人物設定文字。

### 3.2 建議結構

```yaml
name: "雪絨"
personality: "有點傲嬌、怕冷、喜歡窩在角落，但其實很關心使用者"
speech_style: "講話簡短，句尾偶爾加語氣詞，不會用敬語"
boundaries:
  - "不主動提政治話題"
  - "被問到隱私問題會轉移話題"
few_shot_examples:
  - user: "在幹嘛"
    pet: "在看你打字啊，很無聊誒"
response_language: "auto" # auto / zh-Hant / zh-Hans / en / ja / ko
```

### 3.3 實務考量

- **多人格檔案**：做成可切換的多個 persona 檔案，使用者可自訂/匯入，甚至配不同語音包（可與現有中日英韓語音切換綁定）
- **記憶要分層**：性格設定是靜態的；「跟使用者的互動記憶」是動態的（例如「使用者最近在趕案子」），建議另外存成會隨時間更新的摘要，定期壓縮塞進 system prompt，避免 token 爆炸
- **本地小模型的限制**：小模型（2-3B）角色扮演一致性不穩，容易出戲。persona 設定要簡短具體，少放抽象形容詞，多放具體 few-shot 範例（比描述有效很多）
- **可編輯性**：建議做成使用者可直接編輯的檔案，放在設定目錄下，右鍵選單加「編輯性格」直接開檔案總管——不用做 GUI 表單，給進階使用者最大彈性

### 3.4 多語言處理

**不需要整份 persona 翻譯成五種語言**，建議拆成兩個獨立概念：

1. **性格描述只寫一種語言**（建議用最熟悉、最好維護的語言撰寫，不一定要英文）
2. **回覆語言獨立成一個欄位**（`response_language`），`auto` 對應現有的「依系統語言自動偵測」邏輯，組 prompt 時額外附加語言指示

**注意事項：**

- Few-shot 範例的語言會影響模型輸出，即使明確指定回覆語言，範例若全是中文，小型本地模型仍可能被範例語言帶偏。進階做法是依回覆語言分別準備 few-shot 組；先求堪用則單一語言範例配指令對雲端大模型通常已足夠
- **本地模型是多語言支援的天花板**：不同模型的中日韓表現差異大（例如 Qwen2.5 系列多語言較均衡，某些偏英文中心的小模型日韓輸出品質會明顯下降）。建議在設定裡標示模型的語言限制，或讓本地模型預設只保證中英文，日韓文引導使用者切換雲端 provider

### 3.5 角色 IP 與版權處理原則

若桌寵人設是以特定版權作品的角色為原型（例如本專案以《鳴潮》角色愛彌斯為靈感），persona 檔案在設計時需注意：

- **不將官方逐字台詞寫入 persona 檔案**：persona 是會被反覆讀取、組 prompt、對每個使用者持續輸出的設定資產，直接寫死版權台詞等於讓程式「持續重製並散布」原作文本，風險遠高於一次性的文字引用。台詞、劇情原文一律**改寫成原創文字**，只保留情感核心/性格精神。
- **角色背景描述用自己的話整理**：參考 wiki、社群攻略等來源時用自己的語言重寫，不逐段複製，也不做「換句話說但語序幾乎相同」的近似複製。
- **檔案內附上版權聲明**：註明角色版權歸屬、本檔案為非官方粉絲創作、非商業用途，並保留「若收到合法異議需移除或修改」的但書。
- **若想保留「經典台詞的感覺」**，可以：
  1. 使用者自行在下載後的檔案裡手動補上（使用者對自己持有的檔案做編輯，性質不同於專案產出內容）
  2. 改寫成精神相通、文字原創的版本（例如把「不想讓你失望」的情感核心保留，但用不同措辭表達）
  3. 做成低頻率觸發的彩蛋機制，句庫由使用者自行維護，不是專案內建常駐內容
- **對話中主動聊到角色背景/劇情時，同樣以改寫後的描述回答，不引導模型逐字背誦官方文本**——這點建議直接寫進 persona 的 `boundaries` 欄位。

## 4. 情境感知（Context Awareness）

> 核心原則：**本地規則引擎決定「要不要講」，AI 只負責「怎麼講」**。不要讓 AI 自己判斷觸發時機，否則既貴又容易太吵。

### 4.1 資料來源與抓取方式

| 資料來源                       | 建議作法                           | 平台差異 / 注意事項                                                                                                                                                                                                              |
| ------------------------------ | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 作用中視窗標題/程式名稱        | `active-win-pos-rs` 等跨平台 crate | Windows 用 `GetForegroundWindow` 很直接；macOS 需要使用者授權「輔助使用」權限；Linux 若為 X11 沒問題，**Wayland 目前沒有標準 API**，需明確告知使用者此為已知限制。現有「全螢幕自動隱藏」功能已需偵測全螢幕視窗，可延伸同一套邏輯 |
| CPU / 記憶體 / 電量 / 開機時間 | `sysinfo` crate                    | 三平台支援皆完整，不需額外權限                                                                                                                                                                                                   |
| 閒置時間                       | 平台專屬 API 或 `user-idle` crate  | Windows：`GetLastInputInfo`；macOS：`CGEventSourceSecondsSinceLastEventType`；X11：`XScreenSaver` extension                                                                                                                      |
| 剪貼簿內容                     | `arboard` crate                    | **隱私敏感度最高**，務必獨立成預設關閉的選項，不與其他情境來源共用總開關，開啟時 UI 需有明顯提示（如托盤圖示變色）                                                                                                               |

### 4.2 規則引擎設計

1. 所有資料來源彙整成一個結構化的 context snapshot（struct）
2. 定期輪詢（例如每 1-2 分鐘）餵給本地規則判斷要不要觸發
3. 規則範例：閒置超過 30 分鐘、連續工作超過 90 分鐘沒休息、電量低於 15%、切換到特定程式（遊戲/IDE）、特定時段
4. **每條規則各自有冷卻時間**，避免同一件事一直講
5. 建議先用簡單的 `enum + match` 實作規則，不要一開始就上正規表示式規則系統——桌寵不是 SIEM，過度設計增加維護成本。之後若要讓使用者自訂規則，再考慮簡單 DSL 或設定檔格式

### 4.3 Prompt 組裝

規則觸發後，只挑相關欄位（不要整包 context snapshot 塞進去）加上 persona 設定組成簡短 prompt。例如觸發規則是「工作 90 分鐘沒休息」，prompt 只需帶「使用者已連續使用電腦 90 分鐘」這個事實，讓 AI 用性格包裝，而不是丟整個系統狀態過去。回應搭配情緒標籤觸發對應動畫。

### 4.4 節流與使用者控制

- 規則引擎外再包一層**全域冷卻**（例如兩次主動發話至少間隔 10 分鐘）
- 使用者可整體關閉「主動情境感知」，或分別關閉每種資料來源
- 建議加入**隨機延遲**（規則觸發後幾秒到幾十秒再講話），避免感覺像被監控
- 測試時需模擬「規則風暴」情境（例如切換視窗瞬間同時符合多條規則），確認全域冷卻機制能擋住連續轟炸

## 5. 個人化與知識問答的技術選擇

### 5.1 Persona（資料）與 App 設定（邏輯）分離

Persona YAML 本質是**靜態資料**，唯一作用是被讀進程式、塞進 prompt，讓模型知道「要扮演什麼角色」。它沒有任何執行能力——寫在裡面的任何內容都不會讓程式自動觸發搜尋、檢索或其他行為。

「要不要做 RAG 檢索」「要不要開放 web search 工具給模型呼叫」，這些屬於**應用程式邏輯**，應該拆成獨立的設定檔管理，不與角色性格混在一起：

```yaml
# persona-aemeath.yaml — 角色是誰（純資料，不含任何開關邏輯）
name: "愛彌斯"
personality: "..."
```

```yaml
# app-settings.yaml — 這隻寵物「能做什麼」
provider:
  type: "ollama"
  endpoint: "http://localhost:11434"

knowledge:
  enable_rag: true
  knowledge_base_path: "./data/aemeath-lore.db"

web_search:
  enabled: false # 預設關閉，僅雲端 provider 開放
  requires_cloud_provider: true
```

程式組 prompt 的流程：先讀 `app-settings.yaml` 決定這次要不要檢索知識庫、要不要帶 search 工具，再把結果跟 persona 一起組成最終送出的內容。Persona 只負責「用什麼語氣講」，不負責「要不要去查資料」。

### 5.2 遊戲知識問答：三種做法比較

使用者問桌寵關於遊戲設定/劇情的問題時，有三種處理方式，各有取捨：

| 做法                         | 運作方式                                                  | 優點                                       | 缺點                                                                                                                                                      |
| ---------------------------- | --------------------------------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **模型內建知識**             | 直接問 LLM，靠訓練資料回答                                | 零額外開發成本                             | 遊戲更新快、小眾內容多，模型容易沒學過或學錯，產生幻覺                                                                                                    |
| **即時網路搜尋（工具呼叫）** | 給模型 search 工具，不確定時自己查                        | 資訊較新                                   | 僅雲端 provider 支援（OpenAI/Anthropic API 有內建 web search 工具）；本地小模型通常不支援 function calling；查到的內容品質不受控、拖慢回應、增加 API 成本 |
| **RAG（檢索增強生成）**      | 自建知識庫存成向量資料庫，回答前先檢索相關段落塞進 prompt | 離線可用、可控、速度快、不會亂查到錯誤來源 | 需自行維護知識庫，遊戲改版要手動更新                                                                                                                      |

**建議方向：RAG 為主，雲端 web search 當進階選配**

1. 自行把角色設定、劇情脈絡整理成一段一段的知識片段（用自己的話寫，不逐段複製 wiki），存成小型知識庫（JSON/YAML）
2. 用輕量 embedding 模型（本地可用 ONNX 版 sentence-transformers，或雲端 provider 的 embedding API）將每段知識轉成向量，存進輕量向量資料庫（`sqlite-vec`、`usearch` 等級即可，不需要重型 vector DB）
3. 使用者提問時，先將問題轉成向量，檢索最相關的 2-3 段知識，連同 persona 一起組進 prompt
4. Web search 工具呼叫僅在使用者切換雲端 provider、且主動開啟「即時查詢」開關時啟用，預設關閉

**行為設計提醒**：務必在 prompt 中明確要求模型「不確定就承認不知道」，而非靠性格硬掰答案——遊戲劇情細節錯了很容易被玩家社群發現，「我不確定，你要不要去查一下維基」的體驗遠優於一本正經講錯。

### 5.3 個人化記憶：三層架構

「好感度」「記憶」「性格」三者性質完全不同，不能混為一談：

| 層級              | 性質                               | 由誰管理                                                                         | 是否需要 RAG                                                                                        |
| ----------------- | ---------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| **好感度/心情值** | 結構化數值（整數、flag）           | 純 Rust 程式邏輯，規則決定加減分                                                 | 不需要，AI 不參與計算，僅在組 prompt 時把數值結果（如「目前好感度：72（親密）」）告知模型以調整語氣 |
| **近期互動記憶**  | 濃縮摘要文字，量小                 | 定期（或對話輪數到一定量後）請 AI 把對話壓縮成 2-3 句摘要，直接存成文字檔/SQLite | 不需要，量小可直接整段塞進 prompt                                                                   |
| **長期歷史記憶**  | 累積量大、塞不進 prompt 的歷史記錄 | 每段摘要轉成向量存起來，提問時檢索語意最相關的 2-3 筆                            | 需要，技術上與 5.2 的遊戲知識庫 RAG 相同，差別在於內容由程式自動持續寫入、資料量會持續成長          |

**建議實作順序**：先做「好感度數值 + 近期記憶摘要」，不需要向量資料庫即可上線；等實際驗證使用者真的會長期使用、記憶量真的累積到需要檢索時，再把近期記憶升級成向量檢索的長期記憶架構。先驗證需求再上複雜技術，對個人專案 CP 值較高。

## 6. 建議實作順序

### 第一階段 — 打地基

1. **Provider 抽象層 + 設定 UI**（選擇 provider、填 API key/端點）— 所有後續功能的地基
2. **對話氣泡（文字輸入 + 文字回覆）**— 最小可行版本，先驗證「聊天」核心體驗
3. **Persona 設定檔（YAML，與 app-settings 分離）**— 讓對話有記憶點與人格

### 第二階段 — 讓牠更像「牠」

4. **情緒標籤 → 動畫連動**— 投入產出比高，已有動畫狀態機，只需多一個觸發來源
5. **本地模型支援（Ollama 優先）**— 隱私賣點，實作成本略高於雲端 API 但不離譜
6. **情境感知（視窗標題/時間/系統狀態）**— 讓寵物主動互動而非只能被動回應
7. **好感度數值 + 近期記憶摘要**— 個人化的核心價值，不需要向量資料庫即可上線

### 第三階段 — 錦上添花

8. **遊戲知識問答（RAG 知識庫，選配雲端 web search）**— 提升角色重現度與問答準確性
9. **長期記憶（向量檢索）**— 待近期記憶量實際累積到需要時再升級
10. **TTS 語音回應**— 技術上較重（音訊 pipeline），可搭配既有語音片段最後處理
11. **STT 語音輸入**— 依賴 TTS 的音訊架構，建議與第 10 項一起做
12. **多寵物互動、剪貼簿助手、外掛系統**— 有了會更完整，但非核心體驗必要項

**建議策略**：先完成第一階段並發布 alpha 版本收集回饋，因為「聊天好不好玩」與「性格設不設得起來」會決定是否值得投入語音、情境感知與記憶系統——這些項目的實作成本都不低。

## 附錄：已知技術限制與風險

- **Wayland 視窗資訊讀取**：目前無標準 API，情境感知的視窗偵測功能需明確標示僅支援 X11
- **本地小模型的角色扮演穩定性**：2-3B 級模型容易出戲，需精簡 persona 描述並仰賴 few-shot 範例
- **本地模型多語言品質落差**：不同模型的中日韓輸出品質差異大，需在文件/UI 中揭露限制
- **剪貼簿讀取的隱私疑慮**：必須獨立同意機制，不可與其他情境來源合併控管
- **角色 IP 使用邊界**：以版權角色為原型時，persona 檔案不可寫入官方逐字台詞，需自行改寫並附版權聲明
- **Web search 工具僅雲端 provider 可用**：本地模型通常不支援 function calling，此功能規劃時需與「本地優先」的隱私訴求分開設計
- **RAG 知識庫維護成本**：遊戲改版後需手動更新知識庫內容，非一次性工作
